# 점프부기 Web 버전 이식 및 반응형 UI 설계 지침

> **문서 상태: 웹 이식 당시의 설계 요구사항.** 아래 원문은 설계 의도를 보존한 자료이며 현재 구현 완료 목록이 아닙니다. 이 문서가 실제 AI 프롬프트로 제출되었는지는 확인되지 않았습니다. 현재 구현과 호출 관계는 [ARCHITECTURE](ARCHITECTURE.md), 당시 웹 점검 결과와 한계는 [WEB_REVIEW](WEB_REVIEW.md), 미완료 개발은 [TODO](TODO.md)를 확인합니다. 현재 웹은 GitHub Pages에 정적 배포되어 브라우저별 로컬 기록을 제공하며, 아래의 서버 DB·온라인 통합 랭킹·분석용 수집과 서버 점수 검증은 향후 개발 대상입니다. 프롬프트의 출처와 재사용 기준은 [프롬프트 관리](prompts/README.md)에 둡니다.

현재 Pygame 버전을 기준으로 Web 버전으로 이식한다.

중요한 전제:

- 기존 Pygame 버전은 Raspberry Pi의 작은 화면을 고려하여 논리 화면 크기가 작게 설계되어 있다.
- Pygame 버전의 기본 게임 규칙과 기능은 유지한다.
- Web 버전에서는 PC 브라우저와 모바일 브라우저에서 모두 플레이할 수 있도록 반응형 웹으로 구성한다.
- Web과 Mobile을 별도의 게임으로 만들지 않는다.
- 하나의 게임 로직을 공유하고, 입력 방식과 화면 배치만 기기 환경에 맞게 다르게 처리한다.
- 첫 Web 버전에서는 기능을 과도하게 추가하지 않는다.
- 우선 Pygame 버전의 플레이 경험을 Web으로 옮기고 화면 구조와 밸런스를 확인하는 것이 목적이다.

---

# 1. Pygame과 Web의 화면 크기 차이

현재 Pygame 버전의 논리 해상도는:

```text
Pygame
480 × 360
```

이다.

이 크기는 Raspberry Pi의 작은 LCD에서 구동하는 것을 고려한 구조이다.

Web 버전에서는 단순히 CSS로 화면만 크게 확대하지 않는다.

Web에서는 플레이어가 장애물을 더 일찍 볼 수 있도록 **실제 게임의 논리적 가로 시야를 늘린다.**

첫 번째 실험값으로:

```text
Pygame
480 × 360

Web
640 × 360
```

정도를 사용한다.

중요한 점은 세로 크기를 크게 변경하지 않는 것이다.

세로까지 크게 변경하면 다음 요소들을 다시 조정해야 할 가능성이 높다.

```text
점프 높이
바닥 위치
플레이어 크기
공중 장애물 높이
충돌 위치
```

따라서 첫 Web 버전에서는:

```text
세로 게임 구조 유지
+
가로 시야 확장
```

방식으로 접근한다.

---

# 2. 가로 시야 확장의 목적

가로 화면을 늘리는 목적은 단순히 게임을 크게 보이게 하는 것이 아니다.

핵심 목적은 다음과 같다.

```text
플레이어 앞쪽의 가시 거리 증가
↓
장애물을 더 일찍 확인
↓
장애물 종류 및 패턴 인식
↓
점프 여부 판단
↓
입력
```

후반 난이도에서는 장애물 종류와 패턴이 다양해질 예정이므로 사용자가 반응할 시간을 확보하는 것이 중요하다.

---

# 3. 플레이어 위치

Web 버전에서는 플레이어를 화면 가장 왼쪽 끝에 붙이지 않는다.

화면 전체 가로 길이의 약:

```text
20~25%
```

지점에 플레이어를 배치하는 것을 우선 검토한다.

예:

```text
┌─────────────────────────────────────────┐
│                                         │
│       부기                    장애물     │
│       ↑                                 │
│     20~25%                              │
│                                         │
└─────────────────────────────────────────┘
```

이 구조의 목적은 플레이어 뒤쪽보다 앞쪽 공간을 많이 확보하는 것이다.

즉:

```text
플레이어 뒤 공간
<
플레이어 앞쪽 장애물 확인 공간
```

구조를 만든다.

---

# 4. 장애물 간격과 Spawn

가로 화면이:

```text
480 → 640
```

으로 늘어난다고 해서 장애물 간격을 동일 비율로 늘리지 않는다.

가로 화면 증가 자체로 장애물이 플레이어에게 도달하기까지의 시간이 늘어난다.

즉:

```text
화면 폭 증가
→ 장애물 사전 노출 시간 증가
```

효과가 이미 발생한다.

따라서:

```text
화면 폭 증가
→ 장애물 등장 주기까지 크게 증가
```

하게 만들면 게임이 지나치게 비어 보일 수 있다.

기본 원칙:

```text
기존 패턴 템포 최대한 유지
+
장애물이 더 먼 위치에서 화면에 나타남
+
플레이어가 판단할 시간 증가
```

로 한다.

이렇게 해서 사용자가:

```text
장애물 발견
↓
패턴 파악
↓
점프 결정
↓
점프 입력
```

을 할 시간을 확보한다.

# 5. PC Web 기본 레이아웃

PC에서는 게임 화면과 랭킹보드를 좌우 구조로 배치하는 것을 우선안으로 한다.

예:

```text
┌──────────────────────────────────────────────────────┐
│                                                      │
│   ┌──────────────────────────────┐ ┌──────────────┐ │
│   │                              │ │   Ranking    │ │
│   │          GAME                │ │              │ │
│   │                              │ │ 1. 부기123   │ │
│   │                              │ │ 2. 냥이482   │ │
│   └──────────────────────────────┘ │ 3. ...       │ │
│                                    └──────────────┘ │
│                                                      │
└──────────────────────────────────────────────────────┘
```

게임 영역은 전체 콘텐츠 너비의 약:

```text
70~75%
```

랭킹보드는:

```text
25~30%
```

정도를 사용한다.

---

# 6. 웹 전체 콘텐츠 영역

게임과 랭킹보드를 브라우저 전체 폭에 무조건 늘리지 않는다.

전체 콘텐츠는 화면 가운데 배치한다.

예:

```text
전체 브라우저 화면

        [ max-width 약 1200~1400px ]
       ┌────────────────────────────┐
       │     GAME     │  RANKING    │
       └────────────────────────────┘
```

게임 화면은 PC 브라우저에서 전체 화면을 가득 채우기보다 적어도 화면의 약 2/3 정도 또는 그보다 약간 작은 크기로 보이도록 한다.

즉 게임 자체에 집중할 수 있도록 가운데 정렬된 콘텐츠 영역을 만든다.

---

# 7. PC 권장 구조

PC에서의 권장 구조:

```text
                    PC
──────────────────────────────────────

        게임 약 70%       랭킹 약 30%
      ┌───────────────┐ ┌─────────┐
      │               │ │ Ranking │
      │   GAME        │ │         │
      │               │ │         │
      └───────────────┘ └─────────┘

           중앙 콘텐츠 영역
```

랭킹은 게임 플레이에 반드시 필요한 정보는 아니므로 오른쪽 보조 영역에 배치한다.

---

# 8. 모바일 레이아웃

모바일에서는 PC의 좌우 구조를 그대로 사용하지 않는다.

스마트폰에서는 화면이 좁기 때문에:

```text
GAME | RANKING
```

구조를 사용하면 게임 화면이 너무 작아질 수 있다.

모바일에서는:

```text
GAME
↓
RANKING
```

순서로 세로 배치한다.

예:

```text
                  MOBILE
──────────────────────────────────────

      ┌─────────────────────┐
      │                     │
      │       GAME          │
      │                     │
      └─────────────────────┘

      Score / Best

      ┌─────────────────────┐
      │       Ranking       │
      └─────────────────────┘
```

CSS breakpoint를 이용해서:

```text
Desktop
GAME | RANKING

Mobile
GAME
RANKING
```

구조로 자동 전환한다.

---

# 9. 모바일 플레이 방향

모바일은 가능하면 가로 화면 플레이를 우선한다.

예:

```text
스마트폰 세로
↓
가로 화면 권장 안내

스마트폰 가로
↓
게임 화면 확대
↓
터치 플레이
```

다만 세로 화면에서도 페이지가 깨지거나 사용할 수 없는 상태가 되지 않도록 반응형 구조를 유지한다.

---

# 10. PC와 모바일 입력

게임 로직은 동일하게 사용한다.

PC:

```text
Space
→ Jump
```

모바일:

```text
화면 터치
→ Jump
```

구조는:

```text
keyboard input ─┐
                ├→ jump()
touch input ────┘
```

처럼 동일한 점프 함수로 연결한다.

게임 물리나 플레이어 로직을 PC용과 모바일용으로 따로 만들지 않는다.

---

# 11. 모바일 플레이 중 랭킹 표시

모바일에서 게임을 플레이하는 동안 전체 랭킹을 항상 크게 보여줄 필요는 없다.

플레이 중에는:

```text
현재 점수
내 최고 점수
```

정도만 표시해도 된다.

예:

```text
Score : 124
Best  : 380
```

게임 종료 후 전체 랭킹을 더 자세하게 보여준다.

예:

```text
GAME OVER

Score      324
Survival   02:43

전체 랭킹

1. JumpBugi_31   850
2. Hansung_71    720
3. Cat_221       690
```

---

# 12. 사용자 식별 구조

사용자의 닉네임을 DB의 실제 키값으로 사용하지 않는다.

닉네임은 중복되거나 변경될 수 있기 때문이다.

구조:

```text
player_id
= 실제 유저 식별 키

nickname
= 화면에 표시되는 플레이 이름
```

예:

```text
player_id:
a91d72e8-....

nickname:
JumpBugi_482
```

첫 접속 시:

```text
첫 접속
↓
player_id 생성
↓
랜덤 nickname 생성
↓
localStorage 저장
```

브라우저에는:

```text
localStorage
├─ player_id
└─ nickname
```

을 저장한다.

같은 브라우저에서 다시 접속하면 동일한 player_id를 사용한다.

---

# 13. 초기 플레이 이름

사용자가 별도로 회원가입하지 않아도 게임을 바로 플레이할 수 있도록 한다.

예:

```text
JumpBugi_482
HansungCat_113
Runner_812
```

같은 임시 닉네임을 자동으로 생성할 수 있다.

향후 닉네임 변경 기능은 필요할 때 추가한다.

---

# 14. 향후 DB 기본 구조

향후 서버/DB를 추가할 경우 플레이 결과에는 최소한 다음 데이터를 고려한다.

```text
player_id
nickname
score
survival_time
game_version
played_at
```

이후 데이터 분석을 위해 필요하면:

```text
death_obstacle
season
pattern_id
max_speed
device_type
```

등을 추가할 수 있다.

---

# 15. 플레이 결과 저장 시점

게임 도중 매 프레임마다 DB에 요청하지 않는다.

기본 구조:

```text
게임 플레이
↓
게임오버
↓
플레이 결과 생성
↓
서버 전송
↓
DB 저장
↓
랭킹 계산
↓
랭킹 표시
```

예:

```text
게임 종료
↓
결과 서버 전송
↓
DB 저장
↓
랭킹 계산
↓
랭킹보드 표시
```

이 방식으로 한다.

---

# 16. 랭킹보드 표시 정보

초기 랭킹은 점수를 기준으로 정렬한다.

예:

```text
1. JumpBugi_482
   Score 1,240
   Survival 07:31

2. HansungCat_32
   Score 1,150
   Survival 06:58
```

랭킹에는 우선:

```text
nickname
score
survival_time
```

정도를 보여준다.

# 17. Web 0.1에서는 실제 서버 랭킹을 바로 구현하지 않아도 됨

처음 Web 버전으로 이식할 때부터:

```text
FastAPI
SQLite
실제 사용자 DB
실제 랭킹 서버
```

까지 한꺼번에 구현하지 않는다.

우선:

```text
Pygame
↓
Web 이식

PC 플레이 확인
↓
모바일 플레이 확인
↓
반응형 레이아웃 확인
↓
게임 밸런스 확인
```

순서로 진행한다.

# 18. 첫 랭킹보드는 테스트 데이터 사용 가능

UI 배치를 확인하기 위해 첫 Web 프로토타입에서는 테스트 데이터를 사용할 수 있다.

예:

```text
Ranking

1. TestCat      850
2. JumpBugi     720
3. TestUser     650
```

이 상태에서:

```text
PC에서 게임과 랭킹 위치가 적당한지
모바일에서 랭킹이 게임을 방해하지 않는지
게임 화면 크기가 충분한지
```

를 확인한다.

# 19. 첫 번째 사용자 테스트 목적

첫 배포는 튜터링 친구들을 대상으로 진행한다.

이 단계에서는 서버 데이터 수집보다 게임 자체의 사용성을 먼저 확인한다.

확인할 내용:

```text
링크 접속이 잘 되는가

게임이 바로 실행되는가

화면 크기가 적당한가

PC에서 플레이하기 편한가

모바일에서 플레이하기 편한가

터치 입력이 자연스러운가

장애물이 너무 빨리 오는가

장애물을 확인할 시간이 충분한가

게임이 너무 어렵거나 쉬운가

화면 비율이 어색하지 않은가

버그가 있는가
```

```text
장애물 조기 인식
+
기존 게임 기능 유지
```

# 23. 중요한 구현 원칙

이번 Web 이식에서 가장 중요한 것은 다음이다.

```text
게임을 단순히 확대하지 않는다.

가로 플레이 영역 자체를 넓힌다.

플레이어가 장애물을 더 일찍 볼 수 있게 한다.

PC와 모바일에서 동일한 게임 로직을 사용한다.

레이아웃만 화면 크기에 따라 변경한다.

첫 Web 버전에서는 기존 게임 기능을 임의로 변경하지 않는다.

게임 밸런스는 실제 사용자 테스트 후 수정한다.
```
