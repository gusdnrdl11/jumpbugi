아래는 원래 요청이다. 문서 구조를 위한 공백 정리 외에는 요구사항을 바꾸지 않았다. 마지막의 실행 요청도 실제 대화에 포함되어 있다.

````markdown
# 점프부기 프로젝트 구조 정리 및 기술 학습 체계 구축

## 1. 작업 배경

현재 점프부기(Jump Bugi)는 Python/Pygame 기반의 데스크톱 프로토타입과 HTML/CSS/JavaScript 기반의 웹 버전으로 구성되어 있다.

웹 버전은 GitHub Pages를 통해 배포되어 있으며, 향후 FastAPI와 PostgreSQL을 활용하여 플레이 데이터 수집, 통합 랭킹, 점수 위변조 검증 기능을 구현할 예정이다.

이번 작업의 목적은 새로운 기능을 구현하는 것이 아니라, 기존 프로젝트 구조를 정리하고 향후 개발 및 기술 학습을 위한 기반을 마련하는 것이다.

## 2. 작업 목표

- 기존 프로젝트의 디렉터리 및 문서 구조 정리
- 파이게임과 웹 버전의 독립적인 구조 유지
- 향후 백엔드 및 데이터베이스 확장을 고려한 구조 설계
- 중복 문서 및 불필요한 파일 정리
- 개발 과정에서 사용한 프롬프트 관리 체계 구축
- 개발자가 기존 코드를 분석하고 기술을 직접 습득할 수 있는 학습 체계 구축

## 3. 핵심 작업 원칙

다음 원칙을 반드시 준수한다.

1. 기존 소스 코드의 기능과 동작을 유지한다.
2. 기존 소스 코드를 불필요하게 수정하거나 리팩토링하지 않는다.
3. 기존 파일과 모듈을 추가로 세분화하지 않는다.
4. 새로운 디자인 패턴이나 프레임워크를 임의로 도입하지 않는다.
5. 기존 문서를 우선 활용하고, 필요한 경우에만 새로운 문서를 생성한다.
6. 파일 이동, 이름 변경, 삭제가 필요한 경우 변경 이유와 영향 범위를 먼저 제시한다.
7. 기존 GitHub Pages 배포 및 GitHub Actions 워크플로에 영향을 주지 않는다.
8. 실제로 구현되지 않은 기능을 구현 완료된 것으로 문서화하지 않는다.
9. 확인되지 않은 코드의 역할이나 실행 구조를 추측하여 작성하지 않는다.

## 4. 현재 프로젝트 분석

작업을 시작하기 전에 다음 항목을 분석한다.

- 전체 디렉터리 구조
- 파이게임 버전의 모듈 구성
- 웹 버전의 모듈 구성
- 프로그램 실행 진입점
- 모듈 간 의존 관계
- 기존 테스트 코드 및 개발 보조 도구
- 기존 개발 문서 및 학습 문서
- GitHub Pages 배포 구조
- AGENTS.md에 정의된 개발 지침
- 중복 파일 및 Git 추적이 불필요한 파일

분석 결과를 기반으로 현재 구조의 장점, 문제점, 개선 필요 사항을 구분하여 제시한다.

## 5. 목표 프로젝트 구조

다음 구조를 참고하되, 현재 프로젝트의 구성을 우선하며 불필요한 변경은 진행하지 않는다.
```perl
jumpbugi/                      # GitHub 저장소
├── .github/
│   └── workflows/
├── jumpbugi/
│   ├── desktop_prototype/     # 기존 파이게임
│   ├── web/                   # 기존 웹 게임
│   ├── server/                # 향후 백엔드
│   ├── docs/                  # 프로젝트 문서
│   │   ├── archive/
│   │   └── prompts/
│   ├── image/
│   ├── tests/
│   ├── tools/
│   ├── txt/
│   ├── AGENTS.md
│   └── README.md
├── study/                     # 개인 학습 및 실습
├── .gitignore
└── README.md
```

server 디렉터리는 향후 FastAPI 및 PostgreSQL 연동을 위한 확장 영역으로 정의한다.

이번 작업에서는 백엔드 기능을 구현하지 않으며, 내부 모듈 구성 역시 실제 백엔드 개발 단계에서 결정한다.

## 6. 개발 문서 정리

기존 문서를 분석하고 각 문서의 목적과 책임을 명확하게 구분한다.

| 문서                  | 관리 목적               |
| ------------------- | ------------------- |
| README.md           | 프로젝트 소개 및 실행 방법     |
| ARCHITECTURE.md     | 전체 시스템 구조 및 모듈 간 관계 |
| CHANGELOG.md        | 버전별 변경 이력           |
| TODO.md             | 미완료 작업 및 향후 개발 계획   |
| GAME_IDEA.md        | 게임 기획 및 신규 기능 아이디어  |
| STUDY_NOTES.md      | 파이게임 기술 학습          |
| WEB_REVIEW\.md      | 웹 버전 코드 분석 및 개선 사항  |
| WEB_STUDY.md        | 웹 개발 기술 학습          |
| LEARNING_ROADMAP.md | 전체 기술 습득 순서         |

기존 문서 간 중복 내용이 존재하는 경우 내용을 비교하여 정리 방안을 제시한다.

기존 파일의 이름 변경은 참조 경로와 문서 링크를 확인한 후 진행한다.

향후 백엔드 개발 단계에서는 필요한 경우 다음 문서를 추가한다.

- BACKEND.md
- API.md
- DATABASE.md
- SECURITY.md
- DEPLOYMENT.md

아직 개발되지 않은 기능의 문서는 계획 또는 설계 상태임을 명시한다.

## 7. 아키텍처 문서 작성 기준

아키텍처 문서는 단순한 파일 목록이 아니라 프로그램의 실제 동작을 이해할 수 있도록 작성한다.

다음 항목을 포함한다.

- 전체 시스템 구성도
- 각 디렉터리 및 모듈의 역할
- 프로그램 시작부터 종료까지의 실행 흐름
- 주요 함수와 클래스의 역할
- 모듈 간 호출 관계
- 데이터 생성, 전달, 처리 및 저장 과정
- 기술 선정 이유
- 파이게임과 웹 버전의 구조적 차이
- 향후 백엔드 연동 지점

필요한 경우 Mermaid를 활용하여 실행 흐름과 데이터 전달 구조를 시각화한다.

현재 구현된 구조와 향후 구현할 목표 구조는 명확하게 구분한다.

## 8. 기술 학습 로드맵 작성

이 프로젝트의 주요 목적 중 하나는 AI를 활용한 개발 결과물을 개발자가 직접 이해하고, 이후 독립적으로 설계 및 구현할 수 있는 기술을 습득하는 것이다.

학습 로드맵은 다음 기술을 중심으로 구성한다.

1. Python 및 Pygame
2. HTML 및 CSS
3. JavaScript
4. 게임 루프 및 충돌 판정
5. 모듈화와 프로그램 구조 설계
6. HTTP 및 JSON
7. FastAPI
8. SQL 및 PostgreSQL
9. 프런트엔드와 백엔드 연동
10. Linux 및 클라우드 서버
11. 데이터 검증 및 보안
12. 데이터 수집 및 분석
13. Git 및 GitHub

각 학습 항목에는 다음 내용을 포함한다.

- 학습 목적
- 선행 지식
- 핵심 개념
- 프로젝트 내 관련 파일 및 함수
- 해당 기술이 실제로 적용된 방식
- 권장 코드 분석 순서
- 독립적으로 구현할 수 있는 소규모 실습 과제
- 학습 완료 판단 기준

아직 프로젝트에 적용되지 않은 기술은 향후 학습 항목으로 구분한다.

기존 study 디렉터리는 기술별 독립적인 실습 공간으로 활용한다.

## 9. 프롬프트 관리

docs/prompts 디렉터리를 활용하여 프로젝트 개발 과정에서 사용한 프롬프트를 관리한다.

관리 대상은 다음과 같다.

- 프로젝트 기획
- 아키텍처 설계
- 기능 구현
- 테스트 및 디버깅
- 코드 리뷰
- 리팩토링
- 백엔드 개발
- 배포 및 운영

프롬프트에는 작업 목적, 요구사항, 제한 사항, 결과물 및 검증 기준을 포함한다.

기존 프롬프트가 존재하는 경우 이를 우선 활용한다. 존재하지 않는 과거 프롬프트를 실제 사용했던 것처럼 생성하지 않는다.

API 키, 비밀번호, 인증 파일 등 민감한 정보는 문서 및 Git 저장소에 포함하지 않는다.

## 10. 작업 절차

### Phase 1. 분석

현재 소스 코드, 디렉터리, 문서 및 배포 환경을 분석한다.

### Phase 2. 변경 계획

분석 결과를 기반으로 다음 내용을 제시한다.

- 유지할 구조
- 변경이 필요한 구조
- 추가할 문서
- 수정할 문서
- 중복 및 삭제 검토 대상
- 변경 이유와 예상 영향 범위

**Phase 2 완료 후 작업을 중단하고 개발자의 검토 및 승인을 받는다.**

### Phase 3. 정리

승인된 범위 내에서만 디렉터리와 문서를 정리한다.

### Phase 4. 검증

기존 테스트 및 실행 환경을 활용하여 변경으로 인한 문제가 없는지 확인한다.

- 파이게임 정상 실행 여부
- 웹 버전 정상 실행 여부
- 기존 테스트 통과 여부
- 파일 참조 경로 정상 여부
- GitHub Pages 배포 설정 유지 여부

실행 환경의 제약으로 검증하지 못한 항목은 별도로 명시한다.

### Phase 5. 결과 보고

변경 사항과 검증 결과를 정리하여 보고한다.

## 11. 완료 기준

- 기존 게임 기능 및 소스 코드 구조가 유지되어야 한다.
- 프로젝트 문서의 역할과 관리 목적이 명확해야 한다.
- 기존 문서의 중요한 내용이 손실되지 않아야 한다.
- 백엔드 개발을 위한 확장 방향이 정의되어야 한다.
- 개발자가 전체 코드의 실행 흐름을 추적할 수 있어야 한다.
- 기술별 학습 순서와 직접 구현할 실습 과제가 정리되어야 한다.
- 변경 사항 및 검증 결과를 확인할 수 있어야 한다.

이번 작업의 우선순위는 구조의 복잡성을 높이는 것이 아니라 기존 프로젝트의 유지보수성과 개발자의 기술 이해도를 향상하는 것이다.

별도의 승인 없이 새로운 기능 개발, 대규모 리팩토링, 파일 삭제, Git 커밋 및 원격 저장소 Push를 수행하지 않는다.

이 프롬프트 대로 시작해줘
````
