# 점프부기 웹 버전 스터디 — 코드에서 전체 구조까지

기초 학습 내용은 2026-11-22의 실제 `jumpbugi/web/` 코드와 테스트를 기준으로 하며, 로컬 API·닉네임 설명은 2026-11-27 구현까지 반영해 2026-11-28에 대조했습니다. 웹 게임 버전은 `0.1.0`입니다. 웹 학습 내용은 이 문서 한 곳에서 관리하며 이전 이름과 정리 이력은 [CHANGELOG](CHANGELOG.md)에 보존합니다.

이 문서는 JavaScript와 웹 게임이 처음인 사람을 위한 한 권의 학습 자료입니다. 먼저 게임을 실행하고, 파일 세 개의 역할을 이해한 다음, Space 한 번이 점프로 바뀌는 과정을 따라갑니다. 처음부터 모든 수식을 외울 필요는 없습니다.

전체 기술의 선행 지식·학습 순서·완료 기준은 [LEARNING_ROADMAP](LEARNING_ROADMAP.md), 시스템 구조와 호출 관계는 [ARCHITECTURE](ARCHITECTURE.md), 날짜별 검증 결과와 한계는 [WEB_REVIEW](WEB_REVIEW.md)에서 관리합니다. 이 문서는 HTML/CSS/JavaScript 코드를 읽고 작은 실습으로 확인하는 데 집중합니다. FastAPI·PostgreSQL은 선택적 로컬 모드에 구현되어 있으며 실행은 [BACKEND](BACKEND.md)를 따릅니다. 클라우드 운영·사용자 인증·게임 재연산을 통한 점수 검증은 후속 항목입니다.

코드를 열어 함께 읽을 핵심 파일은 [index.html](../web/index.html), [style.css](../web/style.css), [app.js](../web/src/app.js), [engine.js](../web/src/engine.js), [storage.js](../web/src/storage.js)이며 서버 연동은 [api.js](../web/src/api.js)로 이어집니다. 이 링크와 학습 문서는 저장소 소스 트리를 기준으로 하며, `web/`만 게시하는 GitHub Pages에는 `docs/`가 포함되지 않습니다.

## 1. 먼저 실행해 보기

상위 `pygame/` 폴더에서 PowerShell을 열었다면 다음을 실행합니다.

```powershell
cd jumpbugi/web
python -B serve.py
```

브라우저에서 `http://127.0.0.1:8000/`을 엽니다. Windows에서는 `jumpbugi/web/start_web.bat`을 더블클릭해도 됩니다. 종료할 때는 서버 터미널에서 `Ctrl+C`를 누릅니다.

여기서 Python은 **파일을 브라우저에 전달하는 작은 서버**만 실행합니다. 플레이어 점프와 충돌 계산은 브라우저의 JavaScript가 합니다. 웹 게임 실행에는 Pygame이나 npm 패키지 설치가 필요하지 않습니다. 현재 로컬 서버 코드는 Python 3.10 이상을 기준으로 합니다.

`index.html`을 더블클릭해서 `file://` 주소로 열면 실행되지 않을 수 있습니다. JavaScript 모듈과 자산 목록을 HTTP로 불러오므로 위 서버 주소를 사용하세요. 8000번 포트가 사용 중이면 다음처럼 다른 포트를 씁니다.

```powershell
python -B serve.py --port 8001
```

이 경우 주소도 `http://127.0.0.1:8001/`로 바꿉니다.

### 실행 후 관찰할 다섯 가지

1. 인트로 그림이 2초 동안 보이고, 이후에도 시작하기 전까지 그대로 남습니다.
2. 시작 버튼이나 키 입력 뒤 배경이 1.25초 동안 나타나고 플레이가 시작됩니다.
3. Space로 한 번 점프합니다. 공중에서 다시 눌러도 이중 점프는 하지 않습니다.
4. Esc로 일시정지하면 시간과 점수, 캐릭터 동작도 멈춥니다.
5. 충돌하면 GAME OVER가 나오고 기록판이 바뀝니다. Enter로 바로 다시 달립니다.

게임 화면을 터치해도 시작·점프할 수 있습니다. 다른 탭이나 창으로 이동하면 플레이가 자동 정지합니다. 돌아온 뒤에는 재생 아이콘이나 Esc로 직접 재개합니다.

## 2. 웹을 이해하는 데 필요한 네 가지

| 이름 | 쉬운 설명 | 이 게임에서 하는 일 |
| --- | --- | --- |
| HTML | 화면에 놓을 물건의 목록 | 게임 화면, 시작 버튼, 점수 줄, 기록판 만들기 |
| CSS | 물건의 크기·색·배치 규칙 | PC에서는 좌우 배치, 좁은 화면에서는 위아래 배치 |
| JavaScript | 입력을 받고 값을 바꾸는 코드 | 점프·충돌·득점·그리기·저장 |
| Canvas | JavaScript가 그림을 그리는 도화지 | 배경, 부기, 장애물을 매번 다시 그리기 |

HTML 버튼과 기록판처럼 브라우저가 관리하는 화면 요소들을 **DOM**이라고 부릅니다. Canvas 안에 그린 부기는 DOM 버튼처럼 따로 존재하지 않습니다. 그림을 지우고 새 위치에 다시 그려서 움직이는 것처럼 보입니다.

이 차이를 기억하면 편집 위치를 찾기 쉽습니다.

- 부기와 장애물의 움직임을 바꾸려면 `engine.js`를 봅니다.
- 부기와 장애물을 그리는 방법을 바꾸려면 `app.js`의 `draw()`를 봅니다.
- 기록판의 여백·색·좌우 배치를 바꾸려면 `style.css`를 봅니다.
- 버튼이나 안내 문구의 기본 모양새를 바꾸려면 `index.html`도 함께 봅니다.

```text
pygame/
└─ jumpbugi/
   ├─ desktop_prototype/          Pygame 데스크톱 프로토타입
   │  └─ main.py / backend.py / ... 기존 기능별 Python 모듈
   ├─ image/ / txt/               Pygame 실행 이미지·실제 최고점수
   ├─ docs/                       이 학습 문서·구조·작업 기록·점검 문서
   ├─ server/                     선택적 로컬 FastAPI·PostgreSQL API와 실행 도구
   ├─ tools/verify_local_backend.mjs  Chrome·Edge·로컬 DB 연동 검사
   └─ web/
      ├─ index.html               웹페이지의 뼈대와 버튼

      ├─ package.json             JavaScript 모듈·명령 정보
      ├─ serve.py                 web 폴더를 제공하는 로컬 서버
      ├─ start_web.bat            Windows 실행 도우미
      ├─ src/
      │  ├─ app.js                화면·입력·시작 연출·기록 연결
      │  ├─ engine.js             물리·장애물·충돌·득점·계절
      │  ├─ storage.js            브라우저 식별자와 플레이 결과 저장
      │  └─ api.js                선택적 로컬 서버 전송·재시도·현재 이름 동기화
      ├─ assets/
      │  ├─ manifest.json         그림 경로·크기·프레임·충돌 마스크
      │  ├─ intro.png             인트로 그림
      │  ├─ backgrounds/          사계절 낮·밤 배경
      │  ├─ player/               부기 애니메이션 그림
      │  └─ obstacles/            장애물별 애니메이션 그림
      ├─ tests/
      │  ├─ engine.test.js        게임 규칙 검사
      │  ├─ storage.test.js       기록 저장 검사
      │  └─ api.test.js           서버 모드·대기열·닉네임 동기화 검사
      └─ tools/
         ├─ export_assets.py      Pygame 자원을 웹용으로 내보내기
         └─ browser-smoke.mjs     실제 브라우저에서 주요 흐름 검사
```

처음에는 `app.js`, `engine.js`, `storage.js`의 역할만 기억해도 됩니다.

```text
키보드·터치 ──→ app.js ──→ engine.js
                 │             │
                 │             └─ 새 좌표·점수·충돌 결과 계산
                 ├─ 계산 결과를 Canvas와 HTML에 표시
                 └─ 게임오버 결과를 storage.js에 전달
                                         │
                                         └─ localStorage에 저장
```

`engine.js`는 버튼이나 브라우저 화면을 직접 조작하지 않습니다. 그래서 화면을 켜지 않고 Node 테스트로 물리와 충돌을 검사할 수 있습니다. `storage.js`도 게임 그림을 그리지 않습니다.

위 흐름은 기본 정적 모드입니다. 로컬 API를 실행하고 loopback 주소에 `?server=1`을 붙인 경우에만 `app.js → api.js → FastAPI → PostgreSQL` 전송이 추가됩니다. `web/serve.py`는 이 API를 실행하지 않습니다.

## 4. 소스 코드를 읽기 위한 작은 JavaScript 사전

실제 코드에서 다음 표현을 만나게 됩니다.

| 코드 | 뜻 |
| --- | --- |
| `const canvas = ...` | 나중에 다른 값으로 바꿔 연결하지 않을 변수 선언 |
| `let phase = 'loading'` | 나중에 값이 바뀔 변수 선언 |
| `import { GameEngine } from './engine.js'` | 다른 파일에서 공개한 이름 가져오기 |
| `export class GameEngine` | 다른 파일에서도 쓸 수 있는 클래스 만들기 |
| `new GameEngine(manifest)` | 클래스 설계도로 실제 게임 상태 한 개 만들기 |
| `this.playerY` | 지금 이 게임 객체가 가진 세로 위치 |
| `if (...) return` | 조건이 맞으면 이 함수의 남은 실행을 끝내기 |
| `get slot() { ... }` | `engine.slot`을 읽을 때 계산해서 돌려주기 |
| `value => ...` | 짧게 쓰는 함수 표현 |
| `engine?.score` | engine이 있을 때만 score 읽기 |
| `value ?? 0` | 값이 `null` 또는 `undefined`이면 0 사용 |
| `...array` | 배열의 항목을 펼치기 |
| `Math.floor(2.8)` | 내림해서 2 만들기 |
| `Math.trunc(-2.8)` | 소수 부분을 버려 -2 만들기 |
| `total % 8` | 8로 나눈 나머지 구하기 |
| `===` | 값과 자료형이 같은지 비교하기 |

`const`로 만든 객체도 내부 속성을 바꿀 수 있습니다. `const engine = ...`이라고 썼다는 이유만으로 `engine.score`까지 고정되는 것은 아닙니다. 설정 객체인 `RULES`는 별도로 `Object.freeze(...)`를 사용해 속성 변경을 막습니다.

`async`와 `await`는 파일·그림처럼 도착을 기다려야 하는 일을 표현합니다. 기다리는 동안 브라우저 전체를 멈추는 `while` 반복문을 쓰는 것과는 다릅니다.

## 5. 브라우저가 처음 페이지를 열면

`jumpbugi/web/index.html`의 `<head>`에 두 연결이 있습니다.

```html
<link rel="stylesheet" href="./style.css">
<script type="module" src="./src/app.js"></script>
```

첫 줄은 CSS를 불러오고, 둘째 줄은 JavaScript 시작 파일을 불러옵니다. `type="module"`이므로 `app.js` 안에서 `import`를 쓸 수 있습니다.

이후 `app.js` 마지막의 `load()`가 실행됩니다. 읽는 순서는 다음과 같습니다.

1. `PlayerStore`로 브라우저 ID와 이전 기록을 준비합니다.
2. `renderLeaderboard()`로 기록판을 만듭니다.
3. `fetch('./assets/manifest.json')`으로 자산 목록을 읽습니다.
4. 목록에 들어 있는 이미지들을 `new Image()`와 `Promise.all(...)`로 불러옵니다.
5. `prepareIntroArtwork()`로 화면 표시용 인트로를 준비합니다.
6. `new GameEngine(manifest)`로 게임 상태를 만듭니다.
7. `changePhase('splash')`로 인트로 단계로 바꿉니다.
8. `requestAnimationFrame(frame)`으로 반복 화면 갱신을 시작합니다.

`manifest`는 “어떤 이미지가 어디에 있고, 크기와 충돌 모양이 무엇인지 적은 목록”입니다. JSON은 이 목록을 파일로 저장하는 형식입니다. JavaScript가 JSON을 읽으면 일반 객체와 배열처럼 사용할 수 있습니다.

이미지를 못 읽으면 `load()`의 `catch`가 로딩 안내를 오류 설명과 다시 불러오기 버튼으로 바꿉니다. 이때 브라우저 개발자 도구의 Console과 Network를 보면 어떤 경로에서 문제가 났는지 찾기 쉽습니다.

## 6. 게임의 단계: 지금 어떤 화면인가

`app.js`의 `phase`는 현재 화면 단계를 나타냅니다.

```text
loading → splash → ready → transition → playing → gameover
           2초     입력 대기    1.25초       │           │
                                          │           └─ Enter/다시 시작 → playing
                                          └─ Esc → 일시정지 ↔ 재개
```

| phase | 화면 | 점수·계절·장애물 진행 |
| --- | --- | --- |
| `loading` | 자산을 준비하는 표시 | 진행 안 함 |
| `splash` | 인트로 그림, 첫 2초는 입력 대기 전 단계 | 진행 안 함 |
| `ready` | 인트로 그림과 시작 아이콘 유지 | 진행 안 함 |
| `transition` | 흰 배경의 부기 뒤로 배경이 나타남 | 배경·달리기 연출만 진행 |
| `playing` | 정상 플레이 | 정지 상태가 아니면 진행 |
| `gameover` | 마지막 게임 화면과 GAME OVER | 모두 멈춤 |

**일시정지는 `phase = 'pause'`가 아닙니다.** `phase`는 `playing`인 채로 `engine.paused`가 `true`가 됩니다. `pause-overlay`라는 HTML 요소 이름과 게임의 단계 이름을 혼동하지 마세요.

`changePhase(next)`는 `phase` 값과 `document.body.dataset.phase`를 바꿉니다. 후자는 HTML의 `data-phase` 속성이 되어 CSS도 사용할 수 있습니다. 예를 들어 CSS의 `body[data-phase="ready"]`는 시작 대기 때의 카드 테두리·그림자를 조절합니다.

`restart()`는 `engine.reset()` 후 바로 `playing`으로 바꿉니다. 따라서 재시작 때는 인트로 2초와 시작 전환을 다시 기다리지 않습니다.

## 7. 가장 먼저 따라갈 코드: Space 한 번이 점프가 되기까지

### 7-1. 입력은 app.js가 받는다

`document.addEventListener('keydown', ...)`를 찾으세요. 이 안에 실제 분기가 있습니다.

```javascript
else if (phase === 'playing' && event.code === 'Space') {
  event.preventDefault();
  jump();
}
```

실제 파일에서는 한 줄로 쓰여 있지만 위처럼 나눠 읽어도 같은 코드입니다. `preventDefault()`는 Space의 기본 동작인 페이지 스크롤 등을 막습니다.

`app.js`의 `jump()`는 시작 대기라면 `start()`를 부르고, 정상 플레이 중이며 정지·게임오버가 아니라면 `engine.jump()`를 부릅니다. 따라서 시작에 쓴 Space가 바로 점프에도 중복 사용되지 않습니다.

터치는 Canvas의 `pointerdown` 이벤트로 같은 `jump()`에 연결됩니다. PC와 모바일에 서로 다른 물리 엔진이 있는 것이 아닙니다.

키보드 처리 앞부분은 길게 눌러 발생한 반복 입력, Ctrl 같은 조합키, 글자 입력 중인 요소 등을 걸러 냅니다. 버튼에 키보드 초점이 있을 때는 해당 버튼의 기본 키보드 조작이 작동하도록 처리합니다.

닉네임 폼이 열려 있으면 전역 게임 키 처리도 즉시 끝냅니다. 폼 자체의 `keydown`은 `stopPropagation()`으로 상위에 전파되지 않게 합니다. 이 두 확인은 입력란 밖으로 초점이 이동한 경우도 보호합니다. Enter 저장·Esc 취소와 한글 조합 중 Enter의 차이는 [15-3](#15-3-닉네임-편집과-게임-입력을-분리하기)에서 이어 봅니다.

### 7-2. 점프 가능 여부는 engine.js가 결정한다

`GameEngine`의 실제 `jump()`입니다.

```javascript
jump() {
  if (this.paused || this.gameOver || this.isJumping) return false;
  this.velocityY = RULES.jumpSpeed;
  this.isJumping = true;
  return true;
}
```

한 줄씩 읽으면 다음 뜻입니다.

1. 정지·게임오버·이미 점프 중이라면 새 점프를 시작하지 않습니다.
2. 세로 속도를 `-15`로 바꿉니다.
3. 점프 중이라는 표시를 켭니다.
4. 실제 위치 변화는 이후 `updateStep()`에서 일어납니다.

즉, 키 입력을 받는 순간 캐릭터를 위로 순간이동시키는 방식이 아닙니다. **점프를 시작할 속도를 주고, 시간에 따라 위치를 계산합니다.**

## 8. 좌표와 시간: 웹 화면이 커져도 같은 게임인 이유

### 8-1. 왼쪽 위가 (0, 0)이다

```text
(0, 0) ─────────────────────→ x 증가
  │
  │          부기
  │          (playerX, playerY)
  │
  ↓ y 증가
(0, 360)                     화면 너비는 640
```

- 오른쪽으로 가면 x가 커집니다.
- 아래로 가면 y가 커집니다.
- 그래서 위로 뛰려면 세로 속도가 음수여야 합니다.
- 이미지 좌표는 그림의 왼쪽 위 기준입니다. 발바닥 좌표가 아닙니다.

`engine.js` 맨 위의 실제 주요 설정입니다.

```javascript
export const RULES = Object.freeze({
  width: 640, height: 360, playerX: 25, groundY: 242,
  physicsHz: 60, gravity: 0.68, jumpSpeed: -15,
  obstacleSpeed: 7, backgroundSpeed: 6, frameTicks: 6,
  slotSeconds: 25, fadeSeconds: 4, passBonus: 10,
});
```

`groundY: 242`는 바닥에 선 부기 이미지의 **위쪽 y좌표**입니다. 캐릭터 발 높이와 구별하세요. 장애물은 각 이미지의 높이에 맞춰 따로 y를 정합니다.

웹의 논리 화면은 640×360입니다. CSS가 휴대폰에서 작게 보여 줘도 게임은 계속 이 좌표계로 계산합니다. Pygame의 480×360 화면보다 가로 공간을 늘렸으며, 세로 물리 기준은 이어받았습니다.

### 8-2. dt는 “직전 화면부터 지난 초”다

`app.js`의 `frame(now)`에서 다음 식을 찾으세요.

```javascript
const dt = previousTime === null ? 0 : Math.max(0, (now - previousTime) / 1000);
```

`now`는 밀리초 단위이므로 1000으로 나눠 초로 바꿉니다. 화면이 약 60번/초 갱신되면 보통 `dt`는 약 `1/60`입니다. 약 30번/초라면 `1/30`입니다.

`requestAnimationFrame(frame)`은 브라우저에 “다음 화면을 그릴 때 이 함수를 다시 불러 달라”고 요청합니다. 정확히 60FPS를 보장하는 명령은 아닙니다.

### 8-3. 물리는 60Hz 기준 단위로 계산한다

`engine.update(dt)`는 초를 물리 계산 단위로 바꿉니다.

```javascript
let remaining = Math.min(seconds, 0.1) * RULES.physicsHz;
```

기준값으로 보면 다음과 같습니다.

| 지난 실제 시간 | 60Hz 기준 이동량 |
| --- | --- |
| 1/120초 | 0.5틱 |
| 1/60초 | 1틱 |
| 1/30초 | 2틱 |

따라서 화면을 더 자주 그리는 기기라고 게임이 두 배 빨라지지 않습니다. 다만 긴 지연이 생기면 이동은 한 번에 최대 0.1초만 따라갑니다. 시간·생존 점수는 전달받은 전체 `dt`를 적용합니다. “시계와 이동이 항상 같은 만큼만 따라잡는다”고 이해하면 코드와 달라집니다.

고속에서는 한 번의 이동을 더 작은 `step`으로 나눠 그 사이마다 충돌을 확인합니다. 장애물이 한 번에 몸을 건너뛰어 충돌 검사를 놓치는 일을 줄이는 장치입니다.

## 9. 점프 계산을 숫자로 이해하기

`updateStep(step)`의 점프 계산 핵심은 다음 두 줄입니다.

```javascript
this.playerY += this.velocityY * step + RULES.gravity * step * (step + 1) / 2;
this.velocityY += RULES.gravity * step;
```

처음에는 식 전체를 외우지 말고 역할을 구분하세요.

- `velocityY`는 현재 위아래 속도입니다.
- `gravity`는 아래쪽으로 속도를 계속 바꿉니다.
- 첫째 줄은 위치를 바꾸고, 둘째 줄은 다음 계산에서 쓸 속도를 바꿉니다.
- `step * (step + 1) / 2` 부분은 기준 물리 틱과 쪼갠 시간 계산을 맞추는 항입니다.

점프 직후 `step = 1`이면 다음과 같습니다.

```text
기존 y = 242, 기존 속도 = -15
새 y = 242 - 15 + 0.68 = 227.68
새 속도 = -15 + 0.68 = -14.32
```

y가 작아졌으므로 위로 올라갔습니다. 반복하면 음수 속도의 절댓값이 줄고, 정점 근처에서 속도가 0을 지나 양수가 되어 아래로 내려옵니다.

바닥에 도착하면 다음 코드가 값을 정리합니다.

```javascript
if (this.playerY >= this.groundY) {
  this.playerY = this.groundY;
  this.velocityY = 0;
  this.isJumping = false;
}
```

이때 `isJumping`이 `false`가 되어 다음 점프를 받을 수 있습니다. 달리기 그림은 반복되지만 공중에서는 플레이어 첫 프레임을 사용합니다.

## 10. 한 화면이 갱신되는 순서

정상 플레이에서 `app.js`의 `frame()`은 다음 흐름으로 읽습니다.

```text
frame(now)
  ├─ 지난 시간 dt 계산
  ├─ engine.update(dt)
  │    ├─ 정지·게임오버면 즉시 종료
  │    ├─ elapsed와 생존 점수 갱신
  │    └─ 작은 step으로 updateStep() 반복
  │         ├─ 배경 스크롤
  │         ├─ 부기 달리기/점프 갱신
  │         ├─ 장애물 이동·동작 갱신
  │         ├─ 통과 보너스 반영
  │         ├─ 충돌 확인 → gameOver 설정
  │         └─ 화면 밖 장애물 교체
  ├─ gameOver이면 finishRun()
  ├─ draw()로 Canvas 다시 그리기
  └─ refreshUI()로 점수·시간·오버레이 갱신
```

**계산하는 함수와 그리는 함수를 구분하는 것**이 구조 이해의 핵심입니다. `draw()`는 “이 위치가 맞는지”를 계산하기보다 엔진이 가진 값을 읽어 그림을 그립니다.

`draw()`는 흰 도화지를 채운 뒤 이전 배경과 다음 배경, 장애물, 부기를 순서대로 그립니다. 시작 단계에서는 같은 함수가 인트로나 전환 화면을 그립니다.

`refreshUI()`는 점수·표시 시간·단계가 같으면 DOM을 매번 다시 고치지 않습니다. 반면 Canvas는 새 화면을 계속 그립니다. 화면 갱신 방식이 서로 다릅니다.

## 11. 충돌: 네모가 겹쳤다고 모두 부딪히지는 않는다

이미지는 네모 파일이지만 주변에 투명한 공간이 많습니다. 네모끼리 겹치는지만 보면 눈에 안 보이는 여백에서도 충돌할 수 있습니다.

이 게임은 `manifest.json`에 저장된 **마스크**를 사용합니다. 마스크는 각 칸에 충돌 몸체가 있는지 적은 작은 지도입니다.

```text
00000
00100
01110
00100
00000
```

`1`은 충돌 검사에 사용하는 부분, `0`은 제외하는 부분입니다. 두 그림을 같은 화면 좌표에 놓았을 때 양쪽의 `1`이 겹치면 충돌입니다.

`collides()` → `drawParts` → `masksOverlap(...)` 순서로 코드를 읽으세요.

1. 현재 부기 애니메이션 프레임의 마스크를 고릅니다.
2. 현재 장애물의 실제 표시 프레임과 좌표를 가져옵니다.
3. 겹칠 수 있는 사각형 범위부터 계산합니다.
4. 그 범위에서 양쪽이 모두 `'1'`인 픽셀을 찾습니다.

그릴 때와 검사할 때 모두 `Math.trunc()` 기준의 정수 좌표를 사용합니다. 장애물 그림과 충돌 좌표가 서로 다른 반올림을 쓰지 않도록 한 것입니다.

마스크는 브라우저에서 PNG를 보고 매번 새로 만드는 것이 아닙니다. `export_assets.py`가 Pygame에서 준비한 마스크를 JSON으로 저장합니다. 원본 기준의 알파 임계값과 장애물 윤곽을 안쪽으로 줄이는 여유도 포함됩니다. 구덩이형은 전용 충돌 프레임을 준비하는 경우도 있어 모든 눈에 보이는 장식 픽셀이 충돌 몸체라고 생각하면 안 됩니다.

그림만 다른 크기로 교체하고 마스크를 그대로 두면 표시와 판정이 달라질 수 있습니다. 이미지·프레임·마스크를 한 묶음으로 관리하는 이유입니다.

## 12. 장애물은 어떻게 고르고 움직일까

### 12-1. 패턴은 등장 순서의 목록이다

`GROUND_PATTERNS`, `SUMMER_PATTERNS`, `CAT_PATTERNS`, `SJ_PATTERNS`를 먼저 보세요. 예를 들어 실제 패턴 하나는 다음과 같습니다.

```javascript
['hsucat.png', 'sj.png']
```

이것은 “한성캣을 보낸 뒤 상찌를 보낸다”는 순서입니다. 배열에 두 이름이 있다고 두 장애물을 즉시 동시에 만드는 것이 아닙니다.

현재 엔진은 `this.obstacle`에 **현재 장애물 단위 한 개**를 둡니다. 상찌 두·세 마리는 이 단위의 `members`에 담아 각 마리를 따로 움직이고 검사합니다.

### 12-2. 등장 선택의 흐름

```text
allows(name)             지금 해금된 장애물인가?
availablePatterns       구성원 모두 해금된 패턴만 모으기
choosePattern()         난이도와 확률을 반영해 패턴 선택
patternQueue            아직 보내지 않은 패턴 구성원 보관
spawnObstacle()         다음 구성원과 동작·좌표 확정
```

첫 장애물은 기본 한성캣·치킨·상찌 중 하나를 고릅니다. 이후에는 대기열을 사용합니다. 다음 장애물은 화면 너비만 고려하지 않고 속도와 `recoverySeconds`를 반영해 이전 점프 후 회복할 시간을 확보합니다.

### 12-3. 계절별 해금

게임 중 실제 경과 시간을 기준으로 합니다. 인트로·일시정지 시간은 포함하지 않습니다.

| 누적 슬롯 | 시각 | 새로 허용되는 주요 내용 |
| --- | --- | --- |
| 0 | 0초, 첫 봄 낮 | 기본 인사 한성캣·치킨·상찌 |
| 2 | 50초, 첫 여름 낮 | 추가 지상·비행 치킨 |
| 4 | 100초, 첫 가을 낮 | 달리기·하품·책 한성캣 |
| 6 | 150초, 첫 겨울 낮 | 달리기 상찌·굴 파기 |
| 8 | 200초, 둘째 봄 낮 | 상찌 무리·탈출, 인사 캐릭터와 상찌의 점프 확대 |

이미 해금된 종류는 계절이 바뀌어도 계속 후보로 남습니다. 생성된 장애물의 동작은 그때 확정하므로, 접근 중 계절 경계를 지났다고 갑자기 새 점프를 선택하지 않습니다.

### 12-4. 모양은 비슷해도 피하는 방법은 다르다

| 장애물 동작 | 기본 대응 |
| --- | --- |
| 지상 인사, 일반 달리기, 낮은 점프 | 부기가 점프로 넘기 |
| 높은 점프·머리 위 점프 | 부기는 지상에서 아래로 통과 |
| 비행형 상·중 높이 | 아래로 통과 |
| 비행형 하 높이 | 점프로 넘기 |
| 굴 파기 상찌 | 지상으로 통과 |
| 탈출 상찌 | 올라오는 몸체를 점프로 피하기 |
| 높은·낮은 상찌가 섞인 무리 | 낮은 마리를 넘으면서 높은 마리 아래로 통과 |

실제 입력 시점은 속도와 몸체 폭에 따라 달라집니다. `obstacleRequiresJump`는 이런 동작 분류를 알려 주며 자동 점프 기능은 아닙니다. 플레이 중 언제 점프할지는 사용자가 결정합니다.

### 12-5. 장애물 점프는 부기 점프와 계산 방식이 다르다

부기는 입력으로 속도를 얻고 중력을 받습니다. 장애물의 정해진 점프는 `makeJump()`와 `jumpPlan()`으로 접근 x좌표에 따른 높이를 계산합니다.

`jumpPlan()`의 실제 식은 다음과 같습니다.

```javascript
-4 * this.height * p * (1 - p)
```

`p`는 점프 구간에서 얼마나 진행했는지를 뜻합니다. `p=0`과 `p=1`일 때 높이 변화는 0이고, `p=0.5`일 때 `-height`가 되어 가장 높이 올라갑니다. 그래서 “가까워지는 동안 올라갔다 내려오는 포물선”이 됩니다.

`makeJump()`는 몸체 폭과 속도, 머리 위 여유 등을 반영해 점프 시작·끝 구간을 정합니다. 상찌 무리는 구성원별로 계획과 출발 흔들림을 가집니다.

## 13. 점수와 시간은 어디에서 바뀌나

### 생존 점수

`update()`에서 이전 정수 초와 새 정수 초의 차이를 점수에 더합니다.

```javascript
const previousSeconds = Math.floor(this.elapsed + 1e-9);
this.elapsed += seconds;
this.score += Math.floor(this.elapsed + 1e-9) - previousSeconds;
```

0.9초에서 1.1초가 되면 `1 - 0`이므로 1점을 더합니다. 프레임을 한 번 그릴 때마다 1점을 주는 방식이 아닙니다. `1e-9`는 아주 작은 수로, 소수 계산 오차 때문에 정수 초 경계를 놓치는 일을 줄입니다.

### 통과 점수

`awardPassBonuses()`는 장애물의 오른쪽 끝이 부기의 x좌표를 지나면 10점을 줍니다. `passed`를 켜서 같은 장애물에 다시 점수를 주지 않습니다.

상찌 무리는 `member.passed`를 따로 확인하므로 두 마리는 총 20점, 세 마리는 총 30점입니다. 앞 마리를 통과한 뒤 뒷마리에 부딪히면 이미 얻은 앞 마리 점수는 남습니다. 이를 위해 통과 보너스를 먼저 처리하고 그다음 충돌을 확인합니다.

살아 있는 동안 약 12초를 달리고 일반 장애물 3개를 넘었다면 점수는 `12 + 3×10 = 42`점입니다. 아래로 통과한 장애물도 같은 보너스를 받습니다.

`formatTime()`은 시간을 `00:12` 같은 문자열로 **보여 주기만** 합니다. 실제 계산용 시간은 `engine.elapsed`의 초 단위 숫자입니다.

## 14. 계절·배경·속도는 같은 시계를 본다

25초가 한 슬롯이며 배경 순서는 다음과 같습니다.

```text
0 봄 낮 → 1 봄 밤 → 2 여름 낮 → 3 여름 밤
    → 4 가을 낮 → 5 가을 밤 → 6 겨울 낮 → 7 겨울 밤 → 0 봄 낮
```

`GameEngine`의 getter 세 개를 읽으면 전체 구조가 보입니다.

```javascript
get totalSlots() { return Math.floor((Math.max(0, this.elapsed) + 1e-9) / RULES.slotSeconds); }
get slot() { return this.totalSlots % 8; }
get cycle() { return Math.floor(this.totalSlots / 8); }
```

| 경과 시간 | totalSlots | slot | cycle |
| --- | --- | --- | --- |
| 0초 | 0 | 0 | 0 |
| 25초 | 1 | 1 | 0 |
| 200초 | 8 | 0 | 1 |
| 225초 | 9 | 1 | 1 |

`totalSlots`는 계속 커지고, `slot`은 화면용으로 0~7을 반복하고, `cycle`은 사계절을 몇 바퀴 완료했는지 나타냅니다. 봄으로 돌아왔다고 속도와 해금까지 초기화되지 않습니다.

`backgroundFrom`, `backgroundTo`, `backgroundAlpha`는 이전 배경과 다음 배경을 4초 동안 섞는 데 쓰입니다. `alpha`가 0이면 다음 배경이 안 보이고, 1이면 완전히 보입니다. `p*p*(3-2*p)`는 시작과 끝의 변화가 부드러운 곡선입니다.

배경은 `backgroundX`를 왼쪽으로 움직이고 같은 이미지를 옆에 한 장 더 그립니다. 한 장이 화면을 벗어나도 뒤에 이어진 그림이 보입니다.

속도는 `speedForSlot()`이 정합니다. 첫 7회 증가는 7%씩이고, 다음 8회 증가는 0.2%씩입니다. 이후 계산에 쓰는 증가 횟수는 더 커지지 않아 현재 설정의 실제 유지 배율은 약 **1.632배**입니다. 코드의 바깥 상한 `1.75`와 실제 도달 배율을 구분하세요.

`difficultyForSlot()`은 속도 외에도 회복 시간, 어려운 패턴 확률, 연속 패턴 확률을 돌려줍니다. 난이도를 바꿀 때는 속도 한 줄만 보는 것보다 이 묶음을 함께 봐야 합니다.

## 15. 게임오버와 기록 저장

### 15-1. 충돌과 결과 저장은 담당자가 다르다

```text
engine.collides()가 true
   → engine.gameOver = true
   → app.js의 frame()이 감지
   → finishRun()
      ├─ 이번 판을 저장했는지 확인
      ├─ store.recordRun(...)
      ├─ renderLeaderboard()
      └─ changePhase('gameover')
```

`recorded`라는 표시가 중복 저장을 막습니다. 엔진은 “충돌했다”는 게임 상태를 만들고, 앱은 “그 결과를 저장하고 종료 화면을 보여 준다”는 연결을 담당합니다.

### 15-2. localStorage는 이 브라우저의 작은 보관함이다

`storage.js`의 `PlayerStore`는 다음 두 이름으로 저장합니다.

```text
jumpbugi.web.v1.identity
jumpbugi.web.v1.results
```

`identity`에는 브라우저를 구분하는 `player_id`와 현재 `nickname`이 있습니다. 닉네임은 바꿀 수 있으며 식별 키는 `player_id`입니다. 로그인 계정이나 인증된 사람을 뜻하지 않습니다. `results`에는 완료한 게임의 결과 목록이 있습니다.

| 결과 필드 | 뜻 |
| --- | --- |
| `player_id`, `nickname` | 이 결과의 사용자 식별자와 플레이 당시 표시 이름 |
| `run_id` | 이번 판을 구분하는 ID |
| `score` | 최종 점수 |
| `survival_time` | 달린 시간, 초 단위 |
| `game_version` | 게임 버전 |
| `played_at` | 저장 시각, ISO 형식 |
| `death_obstacle` | 부딪힌 장애물 이름 |
| `max_speed` | 도달한 속도 배율 |
| `device_type` | 입력 환경을 기준으로 추정한 desktop 또는 mobile |

최근 기록을 중심으로 최대 50개를 보관하고, 오래된 최고 기록은 낮은 점수를 여러 번 기록해도 사라지지 않도록 남깁니다. `leaderboard()`는 점수 내림차순, 동점이면 생존 시간 내림차순으로 상위 5개를 만듭니다.

이때 기본 정적 모드·Pages의 상위 5개는 **플레이 결과 5개**입니다. 같은 `player_id`의 여러 판이 함께 표시될 수 있으며 사용자별로 한 행만 남기지 않습니다. `app.js`의 `renderLeaderboard()`는 현재 브라우저의 ID와 같은 행에 `identity.nickname`을 표시합니다. 따라서 내 100점·70점·50점 세 판이 있을 때 이름을 바꾸면 세 행의 표시 이름이 함께 바뀌어도 점수·시간은 서로 다른 기록으로 남습니다. 다른 ID의 행은 이 이름 변경의 영향을 받지 않으며 저장된 `results.nickname`도 당시 이름 그대로입니다.

기본 정적 모드의 첫 플레이 전 기록판은 `DEMO`에 있는 예시입니다. 결과가 생기면 이 브라우저에 저장한 실제 기록으로 바뀝니다. 같은 출처의 브라우저 저장소가 기준이므로 다른 브라우저·주소·포트에서는 기록이 다르게 보일 수 있습니다. 선택적 로컬 서버 모드가 저장과 조회를 마치면 공동 기록판을 표시하며, 실패하면 브라우저 기록과 재시도 안내를 사용합니다.

공동 기록판은 서버가 사용자별 최고 결과를 한 행씩 고른 목록입니다. `?server=1`이고 서버 상태가 `saved`이며 공동 목록을 받은 경우에만 이 목록을 사용합니다. 그 전이나 실패 시의 대체 표시는 위 로컬 결과 목록입니다. 주소에 `?server=1`이 없는 `/`는 FastAPI가 파일을 제공해도 정적 기록 모드이므로 두 목록의 행 수를 같은 기준으로 비교하지 않습니다.

저장소 접근이 차단돼도 `PlayerStore`는 메모리에 기록을 유지하고 안내를 표시합니다. 이 경우 새로고침 뒤까지 보관되지는 않습니다. Pygame의 `txt/high_score.txt`와 웹 기록은 별개입니다.

### 15-3. 닉네임 편집과 게임 입력을 분리하기

`app.js`의 `canEditNickname()` → `editNickname()` → `saveNickname()`을 차례로 찾습니다. 변경 버튼을 누르면 새 입력창을 만드는 대신 기존 폼의 `hidden`을 해제하고 현재 이름을 넣은 뒤 `focus()`·`select()`로 바로 수정하게 합니다. 열린 폼에서 변경 버튼을 다시 눌러도 작성 중인 내용을 덮어쓰지 않습니다.

| 게임 상태 | 닉네임 편집 |
| --- | --- |
| `ready`·`gameover` | 변경·입력·저장·취소 가능 |
| `loading`·`splash`·`transition` | 변경 불가 |
| `playing`·`playing`에서 일시정지 | 변경 불가 |

`refreshUI()`는 변경 버튼·입력란·저장·취소의 `disabled`를 상태에 맞춥니다. `hidden`은 폼 표시 여부, `disabled`는 조작 가능 여부입니다. 입력란에 `readonly`는 사용하지 않습니다. 편집 함수도 상태를 다시 확인하고, 다른 단계로 넘어가면 폼을 닫으므로 화면에서 버튼만 막는 것으로 끝나지 않습니다.

폼의 Enter는 기본 제출을 통해 저장하고 Esc는 취소합니다. `stopPropagation()`은 게임의 키 리스너까지 이벤트가 올라가지 않게 하며, 입력 자체의 기본 동작을 모두 막지는 않습니다. `isComposing` 또는 키 코드 229로 한글 조합 중임을 확인한 Enter만 `preventDefault()`로 즉시 제출을 막습니다. 따라서 글자를 확정하는 Enter와 닉네임을 저장하는 Enter를 구분합니다.

저장은 `PlayerStore.setNickname()`의 검증을 거칩니다. 원문의 보이지 않는 문자를 거부하고 앞뒤 공백을 정리한 2~12자를 받습니다. 같은 identity 객체의 이름만 바꾸므로 `player_id`·기존 결과·최고값은 남습니다. 취소는 저장소와 서버를 변경하지 않으며 다음에 열면 저장된 이름을 다시 읽습니다.

현재 이름을 여러 로컬 행에 표시하는 동작과 과거 결과 객체를 수정하는 동작은 다릅니다. 먼저 `renderLeaderboard()`의 `displayName`과 `PlayerStore.setNickname()`을 나눠 읽으세요. 표시가 같다는 이유만으로 저장된 과거 이름까지 덮어썼다고 판단하지 않습니다. 2026-11-28에 사용자별 한 행으로 바꿨던 임시안은 원복했으며 현재 구현에는 포함되지 않습니다. 경위와 당시 검증의 범위는 [WEB_REVIEW](WEB_REVIEW.md#2026-11-28-로컬-기록-표시-재판단과-임시안-원복)에 기록합니다.

### 15-4. 로컬 서버에서 현재 이름과 과거 기록 보존하기

서버 모드의 저장은 `setNickname()` → `LocalServerSync.syncIdentity()` → `registerIdentity()` → `POST /api/players` 순서로 이어집니다. `players.nickname`은 현재 이름, `runs.nickname`은 플레이 당시 이름입니다. 공동 랭킹은 현재 이름을 표시하고 과거 결과와 미전송 대기열은 원래 이름을 유지합니다.

판이 끝나면 로컬 결과를 먼저 보관하고 전송할 결과는 `jumpbugi.web.v1.pending`에 저장합니다. 이는 `PlayerStore`의 두 키와 별도로 `api.js`가 관리하는 최대 50개의 재시도 대기열입니다. 과거 로컬 결과 전체를 자동 업로드하거나 닉네임을 바꿀 때 과거 결과를 일괄 수정하지 않습니다. 서버가 꺼져도 로컬 이름·결과를 유지하고 서버 반영을 재시도합니다. 자세한 입력 범위와 DB 보존 검증은 [BACKEND](BACKEND.md)를 봅니다.

## 16. 화면 배치: style.css를 읽는 순서

### 16-1. 게임과 기록판의 바깥 배치

먼저 다음 실제 규칙을 찾으세요.

```css
.play-layout {
  display: grid;
  grid-template-columns: minmax(0, 3fr) minmax(250px, 1fr);
  gap: 24px;
  align-items: stretch;
}
```

넓은 화면에서 게임과 기록판을 약 3:1로 놓는 규칙입니다. 기록판은 최소 250px이므로 모든 화면에서 정확히 75:25인 것은 아닙니다. 전체 영역은 `.app-shell`이 최대 1320px로 제한합니다.

`@media (max-width: 1000px)`에서는 한 열로 바꿉니다. 좁은 화면에서는 게임 → 점수 줄 → 기록판 순서가 됩니다. `@media (max-width: 520px)`에서는 여백·글자·아이콘을 더 작게 조정합니다.

터치 환경의 가로 화면이며 높이가 560px 이하이면 별도의 미디어 쿼리가 게임 너비를 화면 높이에도 맞춥니다. 화면을 회전했을 때는 너비 조건뿐 아니라 이 규칙도 확인하세요. `prefers-reduced-motion` 규칙은 움직임 감소를 요청한 환경에서 로딩 스피너의 회전을 끕니다.

넓은 화면의 `.ranking-card`는 게임 카드가 만든 높이를 따르고, 긴 `.ranking-list`만 안에서 스크롤합니다. 게임오버마다 바깥 기록판을 새로 만들거나 다른 곳으로 옮기는 구조가 아닙니다. 결과가 바뀌면 목록 항목의 내용만 갱신합니다.

### 16-2. 게임 화면의 모양

`.game-stage`의 `aspect-ratio: 16 / 9`는 게임 영역 비율을 유지합니다. `canvas`의 `width: 100%; height: 100%`는 그 안을 채우는 표시 크기입니다.

`app.js`의 `syncCanvasResolution()`은 고해상도 화면에서 그림이 흐려지지 않도록 도화지 픽셀 수를 조절합니다. 배율은 1~2로 제한하고 `context.setTransform(...)`으로 그리기 좌표를 맞춥니다. 도화지가 1280×720으로 준비되더라도 게임 규칙 좌표는 여전히 640×360입니다.

### 16-3. 게임 위에 겹치는 버튼과 안내

`.stage-overlay`는 `position: absolute; inset: 0`으로 게임 영역 위를 덮습니다. 시작·정지·결과 화면은 이 오버레이를 켜고 끄는 방식입니다.

`[hidden] { display: none !important; }`와 `showOverlay()`가 연결됩니다. 모든 오버레이를 지워 버렸다가 다시 만드는 것이 아닙니다.

게임 아래 `.game-hud`의 점수·시간 줄은 계속 같은 위치에 남습니다. 기록판도 플레이 전·중·후에 같은 HTML 영역에 남습니다. 상단 일시정지 버튼은 현재 표시하지 않으며, 키보드 Esc와 화면 이탈 자동 정지를 사용합니다.

아이콘에 글자가 없어도 HTML의 `aria-label`이 “게임 시작”, “계속 달리기” 같은 접근성 이름을 제공합니다. `:focus-visible`은 키보드로 이동할 때 초점을 보여 줍니다.

## 17. Pygame 원본과 웹 코드의 대응

웹 실행은 Python 게임 코드를 직접 호출하지 않습니다. 규칙을 JavaScript로 옮기고 그림·마스크를 준비해 별도 실행할 수 있도록 한 구조입니다. 아래 Pygame 파일명은 모두 `jumpbugi/desktop_prototype/` 기준입니다. 2026-11-22에 소스 위치를 정리했으며 기존 기능별 분리는 유지합니다.

| Pygame에서 찾던 곳 | 웹에서 읽을 곳 | 내용 |
| --- | --- | --- |
| `main.py`의 `JumpBugi` | `app.js`의 이벤트·`frame()`·상태 함수 | 입력, 시작 단계, 반복 실행 |
| `frontend.py`의 `GameView` | `app.js`의 `draw()`·HTML·CSS | 그림과 UI 표시 |
| `backend.py`의 `GameState` | `engine.js`의 `GameEngine` | 플레이어 상태, 물리, 충돌, 득점 |
| `patterns.py` | `engine.js`의 패턴 배열·선택 함수 | 해금된 등장 순서 고르기 |
| `obstacles.py` | `engine.js`의 `makeJump()`·`obstacleFrame`·`drawParts` | 장애물 동작과 포즈 |
| `season.py` | `engine.js`의 슬롯·배경 getter | 계절 순환, 배경 혼합 |
| `difficulty.py` | `speedForSlot()`·`difficultyForSlot()` | 속도, 회복 간격, 패턴 확률 |
| `config.py` | `engine.js`의 `RULES`와 주변 상수 | 웹 규칙 설정 |
| `assets.py` | `tools/export_assets.py` → `assets/manifest.json` | 이미지 프레임과 마스크 준비 |
| `storage.py`와 최고점수 파일 | `storage.js`의 `PlayerStore` | 저장 방식은 브라우저 기록으로 변경 |

주의할 차이는 세 가지입니다.

1. Pygame은 논리 화면이 480×360이고 웹은 640×360입니다.
2. Pygame 시작 대기는 흰 배경의 달리는 부기이고, 웹은 인트로 전체 그림을 시작 입력까지 유지합니다.
3. `config.py` 값을 바꿔도 웹 `RULES`가 자동으로 바뀌지는 않습니다. Python과 JavaScript의 설정은 별도 코드입니다.

자산을 다시 만들 때만 Pygame과 원본 코드가 필요합니다. `jumpbugi/web/`에서 실행하는 명령은 다음과 같습니다.

```powershell
python -B tools/export_assets.py
```

이 도구는 `desktop_prototype/assets.py`가 만든 프레임과 마스크를 읽어 `web/assets/`에 저장합니다. 실제 사용하는 원본 소스·이미지의 해시를 전후로 비교해 원본이 바뀌지 않았는지도 확인합니다. 단순 실행·코드 읽기에는 자산 재생성이 필요하지 않습니다. `manifest.json`의 긴 `0/1` 문자열을 손으로 편집하며 공부할 필요도 없습니다.

## 18. 직접 해 보는 안전한 작은 실습

한 번에 한 가지를 바꾸고, 결과를 본 뒤 원래 값으로 돌려놓으세요. 테스트가 기존 게임 규칙을 확인하므로 규칙을 바꾼 실습에서는 관련 테스트가 실패할 수 있습니다.

### 실습 A. 게임을 바꾸지 않고 상태 관찰하기

게임을 실행한 브라우저에서 `F12` → Console을 엽니다.

```javascript
window.__JUMPBUGI__.phase
window.__JUMPBUGI__.engine.playerY
window.__JUMPBUGI__.engine.isJumping
window.__JUMPBUGI__.engine.score
window.__JUMPBUGI__.engine.totalSlots
```

이들은 현재 값만 읽는 표현입니다. 점프 전후의 `playerY`와 `isJumping`을 비교하세요. Console을 열거나 다른 창을 눌러 자동 정지가 걸리면 게임 화면으로 돌아가 직접 재개합니다.

`__JUMPBUGI__`는 점검을 위해 실행 중 인스턴스를 노출한 통로입니다. 바깥 객체가 고정되어 있어도 안의 엔진 상태까지 모두 읽기 전용인 것은 아니므로, 공부할 때는 위처럼 조회만 하세요.

### 실습 B. 기록판의 간격만 바꾸기

`style.css`의 `.play-layout`에서 `gap: 24px`을 `gap: 32px`로 바꿔 봅니다. 새로고침 후 카드 사이 간격을 관찰합니다. 점프와 점수는 같은 규칙으로 움직입니다. 다시 24px로 돌립니다.

### 실습 C. 점프 높이를 예상하고 확인하기

`engine.js`에서 `jumpSpeed: -15`를 잠깐 `-13`으로 바꿉니다. 위쪽 초기 속도의 크기가 줄었으므로 더 낮게 뛸 것으로 예상할 수 있습니다. 실행해 확인한 뒤 `-15`로 되돌립니다.

기존 장애물 회피 여유가 달라지므로 이 값을 최종 밸런스 변경으로 바로 확정하지는 마세요. 점프 값과 장애물 높이·회복 시간은 연결되어 있습니다.

### 실습 D. 충돌 마스크 예제를 직접 이해하기

`tests/engine.test.js`에서 이름에 `alpha masks`가 들어간 테스트를 찾습니다. 작은 마스크 두 개와 좌표를 그림으로 그려 보고 어떤 위치에서 두 `'1'`이 겹치는지 예상하세요. 이 테스트는 게임 전체를 켜지 않아도 충돌 함수만 검사합니다.

### 실습 E. 저장을 지우지 않고 구조 확인하기

개발자 도구의 Application → Local Storage에서 `jumpbugi.web.v1.identity`와 `jumpbugi.web.v1.results`를 조회합니다. 게임오버 전후의 결과 개수를 비교하세요. 메뉴 이름은 브라우저에 따라 다릅니다. 기존 기록과 Pygame 점수 파일을 삭제할 필요는 없습니다.

## 19. 자동 테스트와 브라우저 점검

### 19-1. 게임 규칙·저장 검사

`jumpbugi/web/`에서 다음 명령을 실행합니다. 개발 검사에는 Node 22 이상을 권장합니다.

```powershell
node --test tests/*.test.js
```

또는 `package.json`의 명령을 통해 `npm test`로 실행할 수 있습니다. 별도 npm 의존성 설치는 필요하지 않습니다.

`engine.test.js`는 다음 질문에 답합니다.

- 30·60·120Hz에서 같은 점프 궤적을 계산하는가?
- 투명한 픽셀을 충돌로 처리하지 않는가?
- 정지·게임오버에서 시간·이동·점수가 멈추는가?
- 계절 해금과 속도 계산이 정해진 기준을 따르는가?
- 마리별 통과 점수가 한 번씩만 붙는가?
- 내보낸 실제 마스크를 쓰는 장애물 동작들을 회피할 수 있는가?

`storage.test.js`는 ID 유지, 결과 필드, 정렬, 잘못된 값 거부, 저장소 차단, 50개 제한, 오래된 최고 기록 보존을 검사합니다.

`api.test.js`는 기본 정적 모드가 API를 사용하지 않는지, 대기열 재시도·진행 중인 닉네임 변경·과거 이름 결과 보존이 맞는지 검사합니다. 2026-11-27에는 이 세 파일의 총 45개 검사가 통과했습니다. 문서를 읽는 날짜의 새 검사 결과와 과거 결과는 구분합니다.

테스트에서 `random: () => 0.9`처럼 난수를 고정하는 이유는 매번 같은 조건으로 재현하기 위해서입니다. `MemoryStorage`는 브라우저 저장소를 흉내 내는 테스트 전용 객체이므로 실제 사용자 기록을 건드리지 않습니다.

### 19-2. 실제 브라우저 흐름 검사

서버가 켜진 상태에서 다른 터미널을 열어 `jumpbugi/web/`에서 실행합니다.

```powershell
node tools/browser-smoke.mjs http://127.0.0.1:8000/
```

이 도구는 설치된 Chrome 또는 Edge를 사용하고 Node의 내장 WebSocket 기능이 필요합니다. PC·모바일 크기를 모사해 화면과 주요 입력 흐름을 검사합니다. 화면과 보고서는 로컬 `web/.qa/`에 저장됩니다.

로컬 FastAPI·PostgreSQL 모드의 닉네임·키보드·터치와 저장 검사는 [BACKEND](BACKEND.md)의 실행 준비 후 `jumpbugi/`에서 `node tools/verify_local_backend.mjs "http://127.0.0.1:8000/?server=1"`로 수행합니다. 이어 `server/local.py verify-report`로 보고서의 UUID를 실제 DB와 대조합니다. 2026-11-27에는 Chrome·Edge 각각 10개 검사 묶음과 직접 SQL 대조가 통과했으며 자세한 범위는 [WEB_REVIEW](WEB_REVIEW.md)에 있습니다. 아래 휴대폰 접속 방법은 정적 게임의 확인이며 loopback 전용 API·DB의 모바일 운영 검증이 아닙니다.

모바일 크기를 흉내 낸 검사와 실제 휴대폰의 성능·터치감 확인은 다릅니다. 실제 휴대폰 확인은 같은 Wi-Fi에서 다음처럼 서버를 연 뒤 PC의 IPv4 주소로 접속합니다.

```powershell
python -B serve.py --host 0.0.0.0
```

PC에서 `ipconfig`로 주소를 찾아 휴대폰에서 `http://PC의IPv4주소:8000/`을 엽니다. 휴대폰의 `127.0.0.1`은 휴대폰 자신을 가리키므로 PC 주소로 바꿔야 합니다. 필요한 경우 Windows의 해당 개인 네트워크 Python 연결 허용 설정을 확인합니다.

### 19-3. Python 원본 검사

Pygame 쪽도 함께 수정했다면 `jumpbugi/`에서 원본 테스트를 실행합니다.

```powershell
python -B -m unittest discover -s tests -v
```

웹 테스트 통과가 Python 테스트 통과를 대신하거나, 반대의 경우를 보장하는 것은 아닙니다. 실행 언어와 상태 객체가 각각 있기 때문입니다.

## 20. 막혔을 때 어디부터 볼까

| 증상 | 먼저 확인할 곳 |
| --- | --- |
| 게임이 열리지 않음 | 서버 터미널이 켜져 있는지, HTTP 주소·포트가 맞는지 |
| 로딩에서 멈춤 | Console 오류와 Network의 manifest·PNG 응답 |
| Space를 눌러도 시작 안 함 | 첫 2초 `splash`가 끝났는지, 버튼 초점·입력 대상 확인 |
| 점프가 안 됨 | `phase`, `engine.paused`, `engine.gameOver`, `engine.isJumping` |
| 게임이 갑자기 멈춤 | 탭·창 이동으로 자동 정지됐는지 확인하고 직접 재개 |
| 점수 계산이 이상함 | `update()`의 생존 점수와 `awardPassBonuses()`를 분리해 확인 |
| 그림과 충돌이 다름 | 표시 프레임·`drawParts`·manifest 마스크를 함께 확인 |
| 게임 화면 크기가 이상함 | CSS 비율과 논리 화면 크기, `syncCanvasResolution()` 구분 |
| 휴대폰에서 접속 안 됨 | 같은 Wi-Fi, 서버의 `--host`, PC IPv4·포트·방화벽 확인 |
| 기록이 다른 주소에서 안 보임 | localStorage의 주소·포트·브라우저가 같은지 확인 |
| 기록이 새로고침하면 사라짐 | 저장소 안내와 `store.persistent` 경로 확인 |
| 닉네임을 수정할 수 없음 | `ready`·`gameover`인지, `canEditNickname`·폼 `hidden`·입력 `disabled`·초점 확인 |
| 닉네임이 DB에 반영되지 않음 | loopback `?server=1`과 로컬 API 실행·서버 상태·재시도 안내 확인 |
| config.py를 바꿨는데 웹이 같음 | 웹의 `RULES`는 별도 JavaScript 설정임을 확인 |

문제를 찾을 때는 “입력 → 상태 계산 → 그림 → 저장” 중 어느 단계가 기대와 다른지 먼저 나누세요. 예를 들어 `playerY`는 바뀌는데 그림이 안 움직이면 입력보다 그리기 경로를 먼저 확인합니다.
