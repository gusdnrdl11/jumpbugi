## 1. 화면에서는 달리지만 플레이어의 x는 고정

한성런은 한성부기가 장애물을 피하는 Pygame 러너입니다. 플레이어는 화면 왼쪽의 `x=0`에 있고, 배경과 장애물이 왼쪽으로 이동합니다. 여러 물체의 상대적인 움직임으로 앞으로 달리는 것처럼 보이게 만드는 방법입니다.

Pygame은 창, 그림, 글꼴, 키 입력과 시간을 다루는 도구입니다. Python의 `random`은 무작위 선택을, `pathlib.Path`는 파일 경로를 담당합니다. 게임을 이해할 때는 화면의 모습과 그 모습을 만드는 숫자를 구분하면 좋습니다. 점프는 그림을 바꾸는 것에 앞서 `player_y`라는 숫자가 바뀌는 일입니다.

## 2. 한 게임을 여러 역할로 나누기

| 파일 | 맡은 일 | 찾아볼 이름 |
| --- | --- | --- |
| `main.py` | 입력과 실행 순서를 연결 | `HansungRun`, `handle_events`, `run` |
| `backend.py` | 위치·점프·충돌·점수와 시간 계산 | `GameState`, `jump`, `update_step` |
| `frontend.py` | 계산된 상태를 그림과 글자로 표시 | `GameView`, `draw`, `sync_background` |
| `config.py` | 여러 파일이 공유하는 수치와 경로 | `SCREEN_SIZE`, `JUMP_SPEED`, `HIGH_SCORE_PATH` |
| `assets.py` | 이미지 로딩·분할·정렬·마스크 준비 | `load_image`, `load_run_frames`, `collision_mask` |
| `storage.py` | 최고점수 파일을 읽고 쓰기 | `load_high_score`, `save_high_score` |
| `tests/` | 정해진 상황에서 결과가 맞는지 검사 | `test_`로 시작하는 검사 함수 |

식당에 비유하면 메인은 진행 담당자, 백은 결과를 만드는 요리사, 프론트는 접시와 진열 담당입니다. 설정은 공통 기준표, assets는 재료 준비, storage는 기록 담당입니다. 이때 백은 인터넷 서버를 뜻하지 않습니다. 모두 같은 컴퓨터에서 실행되는 하나의 프로그램입니다.

```text
main → frontend → assets
main → backend → storage
각 담당 → config
tests → 게임 객체와 동작 검사
```

파일을 나누는 목적은 필요한 코드를 찾고 수정 범위를 줄이기 위해서입니다. 파일 수만 늘려도 게임이 빨라지는 것은 아닙니다. 두 파일로도 만들 수 있지만 이미지 자르기와 저장 코드가 길어지면 규칙과 화면을 읽기 어려워집니다. 반대로 너무 잘게 나누면 import와 파일 사이의 관계를 관리하기 어려워지므로 작은 함수마다 파일을 만들 필요는 없습니다.

## 3. 변수·함수·클래스·self 읽기

변수는 값을 기억하는 이름입니다. `score = 0`은 점수라는 이름에 0을 넣고, `score += 10`은 지금 값에 10을 더합니다. 함수는 관련 작업을 묶습니다. 예를 들어 `reset()`은 새 판 준비, `load_image()`는 이미지 읽기와 크기 조절입니다.

클래스는 관련 데이터와 행동을 묶는 설계입니다. `GameState(...)`로 만든 객체에는 이번 게임의 좌표·점수·상태가 들어갑니다. 메서드는 클래스에 속한 함수이고, `self`는 지금 그 메서드를 실행하는 객체입니다. `self.score`는 그 객체의 점수, `self.jump()`는 그 객체의 점프 동작입니다.

`HansungRun`의 `self.state`에는 `GameState` 객체가, `self.view`에는 `GameView` 객체가 들어갑니다. 따라서 현재 메인에서 점수에 접근한다면 `self.state.score`입니다. 예전 한 파일 구조의 `self.score` 설명을 그대로 메인에 적용하면 안 됩니다.

| 문법 | 의미 |
| --- | --- |
| `=` / `==` | 값 저장 / 같은 값인지 비교 |
| `+=` / `-=` | 기존 값에 더하기 / 빼기 |
| `//` / `%` | 정수 몫 / 나머지 |
| `True`, `False`, `not` | 참, 거짓, 참과 거짓 뒤집기 |
| `return` | 함수 계산을 끝내고 돌아가기 |
| `[]`, `append()` | 목록 만들기, 목록 끝에 추가하기 |
| `{'이름': 값}` | 이름과 값을 연결하는 딕셔너리 |
| `(480, 360)` | 순서가 있는 값 묶음인 튜플 |

`OBSTACLE_HEIGHTS`는 장애물 이름을 높이에 연결한 딕셔너리입니다. `pattern_queue`는 앞으로 등장할 순서를 보관한 목록입니다. `SCREEN_SIZE`처럼 대문자로 쓰는 이름은 설정값이라는 약속이며 Python이 변경을 막는 것은 아닙니다.

## 4. 실행과 import를 구분하기

프로젝트 폴더에서 실행합니다.

```powershell
python main.py
python -B -m unittest discover -s tests -v
```

한 단계 위 폴더에서는 `python -m hansungrun.main`으로 실행할 수도 있습니다. `__init__.py`는 폴더를 패키지로 다루는 데 쓰이며 게임 실행 파일은 아닙니다.

파일 위쪽의 `if __package__:`와 `else:`는 두 실행 방식에 맞는 import를 선택합니다. `from .backend import GameState`의 점은 같은 패키지 안에서 찾는다는 뜻이고, 직접 파일로 실행하는 경우에는 `from backend import GameState`를 사용합니다. 게임 규칙을 두 번 실행하는 코드가 아닙니다.

```python
if __name__ == '__main__':
    main()
```

이 부분은 파일을 직접 실행할 때 게임을 시작하게 합니다. 테스트가 `main`을 import하기만 해도 게임 반복이 자동으로 시작되는 일을 피할 수 있습니다. `main()`은 `pygame.init()`으로 준비하고, `finally`의 `pygame.quit()`로 오류가 발생한 경우에도 정리를 시도합니다.

## 5. 처음 한 번 준비하는 것

`HansungRun.__init__()`은 먼저 `GameView()`를 만들어 창과 이미지·글꼴을 준비합니다. 그 뒤 이미지의 크기, 달리기 프레임 수, 배경 너비와 충돌 마스크를 `GameState(...)`에 전달하고 시간을 재는 시계를 만듭니다.

백은 화면을 만들거나 이미지 파일을 읽지 않아도 전달받은 크기와 마스크로 계산할 수 있습니다. 다만 사각형·마스크를 사용하므로 `pygame` 자체는 import합니다. 프론트가 준비한 정보를 백에 전달하는 것과 백이 직접 파일을 읽는 것은 다른 일입니다.

이미지와 마스크를 시작할 때 준비해 두면 재등장할 때 같은 자산을 골라 쓸 수 있습니다. 화면을 그릴 때마다 디스크에서 PNG를 다시 읽지 않습니다. 달리기 포즈와 정지 안내 같은 표면도 재사용합니다.

## 6. 게임 반복과 Space 한 번의 여행

```text
경과 시간 확인 → 입력 처리 → 상태 계산 → 화면 출력 → 다시 반복
```

이 순서를 맡는 함수가 `run()`입니다. `handle_events()`는 눌린 키와 창 닫기 요청을 읽고, `update(dt)`는 경과 시간에 따라 상태를 바꾸며, `draw()`는 바뀐 상태를 보여 줍니다.

Space를 누르면 메인이 `state.jump()`를 호출합니다. 백은 정지·게임오버·점프 중인지 확인하고, 가능하면 위쪽 속도를 줍니다. 다음 갱신에서 백이 `player_y`를 바꾸고 프론트가 그 좌표에 그림을 그립니다.

```text
handle_events → state.jump → state.update → player_y 변경 → view.draw
```

점프에는 저장할 내용이 없으므로 storage를 거치지 않습니다. 모든 기능이 모든 파일을 통과할 필요는 없습니다. 현재 메인은 `paused` 값을 직접 바꾸기도 하므로 모든 상태 변경을 백의 메서드로만 제한하는 구조는 아닙니다.

## 7. 화면 좌표와 그림 크기

화면의 왼쪽 위가 `(0, 0)`입니다. x가 커지면 오른쪽, y가 커지면 아래로 갑니다. 따라서 `obstacle_x -= 이동량`은 장애물을 왼쪽으로 옮기고, 음수인 점프 속도는 플레이어를 위로 올립니다.

그림의 좌표는 보통 표면 왼쪽 위입니다. `ground_y`도 실제 발바닥 좌표가 아니라 지상에 있을 때 플레이어 표면의 위쪽 y입니다. 현재 `360 - 120 + 2 = 242`이며 실제 발 위치에는 이미지의 투명 여백도 영향을 줍니다.

키가 다른 장애물의 아래쪽을 맞추려면 `y = 화면 높이 - 이미지 높이 + 보정값`처럼 계산합니다. 현재 기본 상찌는 높이 40에 보정값 -2이므로 y=318, 표면 아래끝은 358입니다. 모든 장애물에 하나의 고정 y를 적용하면 작은 장애물이 공중에 뜰 수 있습니다. 유형별 바닥 설정은 현재 구조 문서와 코드를 확인하세요.

`load_image(filename, height=120)`은 원본의 가로세로 비율을 유지합니다.

```text
새 가로 = 원래 가로 × 새 높이 ÷ 원래 높이
```

이미지 파일을 덮어쓰는 것이 아니라 게임에서 사용할 표면의 크기를 조절합니다. `size=(가로, 세로)`를 직접 지정하면 지정한 두 길이에 맞춥니다. 비율 유지와 지정 크기 조절은 목적이 다릅니다.

## 8. FPS와 dt: 더 자주 그려도 같은 속도로

`FPS=120`은 화면 반복의 목표 상한이며 모든 컴퓨터에서 120회를 보장하지는 않습니다. `PHYSICS_HZ=60`은 기존 속도·중력 수치를 시간으로 환산하는 기준입니다.

```python
dt = self.clock.tick(FPS) / 1000.0
```

시계가 알려 준 밀리초를 1000으로 나누면 지난 반복 이후 흐른 초가 됩니다. 기본 속도 6은 기준 시간 한 칸, 즉 1/60초의 이동량입니다. 60FPS에서는 대략 6픽셀씩, 120FPS에서는 대략 3픽셀씩 이동하면 둘 다 기본 초당 360픽셀이 됩니다.

`step`은 이번 계산이 기준 시간 몇 칸인지 나타냅니다. `step=1`은 1/60초, `step=0.5`는 1/120초입니다. `0.05초 × 60 = 3칸`을 작은 단계로 나누면 긴 이동 사이에 장애물을 건너뛸 위험을 줄일 수 있습니다.

현재 `update(dt)`는 양수 경과 시간 전체를 생존 점수와 배경 시계에 반영하고, 물리 이동은 최대 0.1초까지만 따라잡습니다. 창 이동 등으로 오래 지연되었을 때 즉시 멀리 순간이동하지 않도록 하는 선택입니다. 모든 시간 계산이 0.1초로 제한되는 것은 아닙니다.

속도가 누적해서 빨라지므로 세부 단계도 `1 / speed_multiplier` 이하로 나눠 장애물 이동량이 한 번의 충돌 검사 사이 최대 6픽셀이 되게 합니다. `1e-9` 같은 작은 오차 허용값은 실수 계산의 끝자리 오차 때문에 경계를 놓치거나 아주 작은 남은 시간을 계속 계산하는 일을 줄입니다.

누적 가속은 현재 `1.05 ** floor(경과 초 / 30)`입니다. 30초마다 직전 속도에 5%를 더하므로 두 번 전환한 배율은 `1.05 × 1.05`입니다. 계절의 그림 번호는 반복되어도 누적 경과 시간은 유지하므로 다음 봄에 속도가 처음으로 돌아가지는 않습니다.

## 9. 점프·중력·착지

점프를 시작하면 `velocity_y = JUMP_SPEED`, `is_jumping = True`로 바꿉니다. 현재 시작 속도는 -15이며 중력 0.6이 아래 방향 속도를 더합니다. 기준 시간 한 칸마다 속도는 `-15 → -14.4 → -13.8 → … → 양수`로 변합니다. 음수일 때 올라가고 양수일 때 내려갑니다.

현재 백의 위치 계산은 다음과 같습니다.

```python
self.player_y += self.velocity_y * step + GRAVITY * step * (step + 1) / 2
self.velocity_y += GRAVITY * step
```

현재 속도로 이동한 거리와 중력이 더한 거리를 합칩니다. `step + 1`이 들어가는 식은 기존 한 칸씩 계산하던 움직임을 유지하면서 더 작은 단계로 나누어도 같은 궤적을 따르도록 맞춘 것입니다. 모든 게임에서 그대로 쓰는 일반 공식이라고 외우기보다 이 프로젝트의 시간 단위와 함께 읽으세요.

내려오다 `player_y >= ground_y`가 되면 지상 좌표로 맞추고 속도를 0, 점프 상태를 False로 돌립니다. 이미 점프 중이면 다시 Space를 눌러도 속도를 새로 주지 않으므로 이중 점프가 되지 않습니다. 점프 속도나 중력을 바꾸면 높이뿐 아니라 착지 시간과 장애물 회피 구간도 다시 확인해야 합니다.

## 10. 배경 스크롤·계절·혼합

같은 긴 배경을 `background_x`와 `background_x + background_width`에 두 번 그립니다. 한 장이 빠져나갈 때 다른 장이 빈 곳을 채웁니다. 파일을 두 번 읽는 것이 아니라 같은 표면을 두 번 사용하는 것입니다.

`%`는 이동 거리를 배경 너비 안에서 반복하게 합니다. 끝을 넘은 거리도 보존하면 경계에서 멈추거나 튀지 않습니다. 배경과 장애물에는 같은 속도 배율을 적용합니다.

계절 전환에서는 백이 이전 이미지 번호, 다음 이미지 번호와 혼합도를 계산하고 프론트가 두 이미지를 합성합니다. `background_alpha`는 이 이미지 쌍을 섞는 정도이고, `night_alpha`는 낮밤 밝기에 맞춰 점수 글자색을 정할 때 사용합니다. 현재는 알파값 하나만으로 어느 계절 그림인지 정하지 않습니다.

전환의 시작과 끝을 부드럽게 만드는 `p * p * (3 - 2 * p)`와 같은 보간식도 배울 수 있습니다. 프론트 캐시는 이미지 번호 두 개와 혼합도를 함께 비교합니다. 알파가 같아도 계절이 다르면 다시 그려야 하기 때문입니다. 재사용하는 합성 표면은 원본 배경을 바꾸지 않도록 구성합니다.

## 11. Surface와 애니메이션 시트

`Surface`는 그림을 올릴 수 있는 도화지입니다. `blit()`는 다른 표면 위에 그림을 올리고, `font.render()`는 글자를 표면으로 만듭니다. `convert_alpha()`는 캐릭터 주변 투명도를 유지하고, 배경에 쓰는 `convert()`는 불투명 표면으로 변환합니다. `smoothscale()`은 크기를 부드럽게 바꿉니다.

시트는 여러 포즈를 모은 이미지입니다. 플레이어의 2×2 시트는 행과 열을 순회해 0→1→2→3 순서로 분리합니다. `subsurface()`는 필요한 영역을 잡고, `copy()`는 그 영역을 따로 복사합니다. `get_bounding_rect(min_alpha=20)`은 거의 투명한 여백을 제외한 범위를 찾습니다.

각 포즈를 따로 높이에 꽉 맞추면 몸통 크기가 프레임마다 달라질 수 있습니다. 공통 배율을 쓰고 같은 중심·발 위치에 정렬하면 크기와 발 위치가 흔들리는 현상을 줄일 수 있습니다. 머리 위치까지 같아지는 것은 아니므로 재생 모습도 확인합니다. 현재 플레이어는 머리부터 발까지 전체 포즈를 사용합니다.

`RUN_FRAME_TICKS=6`이면 기준 시간 6칸, 즉 0.1초마다 다음 포즈입니다. 실제 화면을 여섯 번 그린다는 뜻은 아닙니다. 120FPS에서는 같은 포즈를 대략 12번 그리며 네 포즈 한 바퀴는 0.4초입니다. 점프 중에는 첫 포즈를 사용하고 달리기 시간은 멈춥니다. 착지하면 멈춘 시간부터 이어갑니다.

일반 달리기·날갯짓은 나머지 연산으로 반복하지만, 상찌의 굴 파기는 접근 거리에 따라 단계를 고르고 마지막 구덩이에서 멈춥니다. 상황에 따라 애니메이션 기준을 시간이나 거리로 정할 수 있다는 예입니다. 여러 기본 상찌를 한 표면에 나란히 붙인 묶음은 개별 크기를 유지하는 합성 자산의 예입니다.

## 12. 무작위 패턴과 등장 조건

`random.choice(후보)`는 후보 중 하나를 고릅니다. 같은 결과가 연속으로 나올 수도 있습니다. 현재는 시작 장애물을 고르는 일과 이후 패턴을 뽑는 일을 구분합니다. 패턴은 순서의 묶음이며, 뽑은 순서를 대기열에 넣고 앞에서 하나씩 꺼냅니다.

새 장애물에는 해금 시간이 있습니다. 후보에서 제외하는 것과 대기열에 남아 있는 잠긴 유형을 제거하는 일을 함께 확인해야 첫 등장 조건을 지킬 수 있습니다. 조건을 누적 플레이 시간으로 판단하면 계절 이미지가 다음 봄으로 돌아와도 이미 해금한 유형을 유지할 수 있습니다. 재시작할 때 시간과 대기열을 초기화하면 첫 바퀴 제한이 복원됩니다.

장애물은 기본적으로 하나가 화면을 완전히 나간 뒤 다음 활성 장애물을 준비합니다. 속도가 빨라져도 착지와 다음 판단 시간을 확보하려고 접근 거리를 늘립니다. 2·3마리 상찌 묶음은 한 활성 장애물 안에 여러 그림을 함께 담은 경우입니다. 별도 장애물을 여러 개 동시에 관리하는 구조와 구별해서 읽으세요.

## 13. 사각형 후보 검사와 픽셀 마스크

`pygame.Rect`는 그림을 둘러싼 사각형입니다. `colliderect()`로 사각형이 겹치는지 먼저 확인하면 멀리 떨어진 물체에 불필요한 정밀 검사를 하지 않을 수 있습니다. 다만 투명 여백까지 포함한 사각형만으로 판정하면 보이는 윤곽과 어긋날 수 있습니다.

현재는 사각형이 겹칠 때 마스크를 비교합니다. 마스크는 충돌 픽셀이 있는 곳을 기억하는 표입니다. 출력 크기로 조절한 이미지에서 알파값이 127보다 큰 픽셀을 사용하고, 장애물 마스크는 높이 비율에 따라 가장자리를 안쪽으로 깎습니다. 현재 비율은 6%이고 최소 1픽셀입니다. 8방향 이웃이 모두 채워진 픽셀만 남기는 작업을 반복해 윤곽을 줄입니다. 희미한 반투명 픽셀과 테두리 접촉에 여유를 두는 방법입니다. 여백과 구멍을 큰 사각형으로 채우지는 않습니다.

플레이어와 장애물의 실제 포즈에 해당하는 마스크를 선택하고, 화면에 그릴 때와 같은 `int()` 좌표를 사용합니다. 소수 좌표와 정수 출력 좌표가 다르면 눈에 보이는 위치와 충돌 계산이 어긋날 수 있기 때문입니다. 작은 단계로 검사해도 연속 궤적의 모든 지점을 검사하는 방식은 아니라는 범위도 이해해야 합니다.

과거 설명의 `inflate(-50, -35)`는 중심을 유지하면서 전체 가로 50, 세로 35를 줄이는 사각형 보정입니다. 양쪽에서 각각 50씩 줄인다는 뜻이 아닙니다. 이것은 `Rect`를 배우는 예로 남겨 두며, 현재 충돌을 조절할 때는 `COLLISION_ALPHA_THRESHOLD`, `OBSTACLE_MASK_INSET_RATIO`, 최종 프레임과 마스크를 확인합니다.

## 14. 점수를 한 번만 주기

장애물의 전체 사각형 오른쪽 끝이 플레이어 왼쪽을 지나면 통과 보너스를 줍니다. 이 기준은 안쪽으로 깎은 충돌 윤곽과 다릅니다. `passed`는 이 장애물의 보너스를 이미 받았는지 기억합니다. 없으면 통과 후 매 갱신마다 점수가 계속 오를 수 있습니다. 다음 장애물을 준비할 때 False로 돌립니다.

현재 점수는 통과 보너스와 생존 점수를 합칩니다. 온전한 1초마다 생존 점수를 더하려고 이전 정수 초와 새 정수 초의 차이를 계산합니다. 0.5초씩 두 번 진행해도 1점을 주고, 두 초 경계를 한 번에 지나면 지나간 초만큼 주는 방식입니다.

`SCORE`는 이번 판 점수, `BEST`는 확정해서 저장한 최고점수입니다. 플레이 중 SCORE가 BEST보다 커도 BEST는 판이 끝나거나 종료할 때 갱신될 수 있습니다. 화면에서는 현재 점수의 오른쪽 끝을 고정하고 글자 폭을 계산해 최고점수를 그 왼쪽에 배치합니다.

## 15. Path와 최고점수 저장

변수는 프로그램이 끝나면 사라지므로 다음 실행에도 남길 기록은 파일에 씁니다. 현재 경로는 `config.py`의 위치를 기준으로 계산합니다.

```python
PROJECT_DIR = Path(__file__).resolve().parent
IMAGE_DIR = PROJECT_DIR / 'image'
HIGH_SCORE_PATH = PROJECT_DIR / 'txt' / 'high_score.txt'
```

`__file__`은 코드 파일의 위치, `resolve()`는 해석된 절대 경로, `parent`는 부모 폴더입니다. `Path`의 `/`로 하위 경로를 연결할 수 있습니다. 터미널의 현재 폴더가 달라도 같은 자산을 찾으며, 프로젝트를 옮길 때 내부 `image/`와 `txt/`도 함께 옮깁니다.

백은 언제 신기록인지 판단하고 storage는 읽고 쓰는 방법을 담당합니다. `load_high_score()`는 파일 글자를 정수로 바꾸며 파일이 없으면 0을 돌려줍니다. 숫자가 아닌 내용이나 음수 기록을 자동으로 고치는 코드는 없습니다.

저장은 `high_score.tmp`에 먼저 쓴 뒤 실제 기록 파일을 교체합니다. 기존 파일을 바로 비우고 다시 쓰는 위험을 줄이는 방식이며 모든 저장 실패를 막는 것은 아닙니다. 최고점수는 매 통과가 아니라 게임오버 또는 종료 요청 시 신기록이면 저장합니다. Esc로 잠시 멈추는 것만으로 저장하지는 않습니다. 읽기·저장 방식을 바꿀 때는 storage의 호출 방식도 함께 확인합니다.

## 16. 정지·게임오버·종료·새 판

| 상태 | 멈추는 것과 계속하는 것 |
| --- | --- |
| `paused=True` | 이동·점프·점수·계절·애니메이션 갱신을 멈추고 안내 출력과 입력 처리는 계속 |
| `game_over=True` | 이번 판 계산을 멈추고 Enter 재시작과 종료 입력을 계속 처리 |
| `running=False` | 메인 반복을 끝내 프로그램 종료로 진행 |

`paused = not paused`로 참과 거짓을 번갈아 바꾸면 Esc가 정지·재개 버튼이 됩니다. Space는 점프, 게임오버 후 Enter는 재시작, Ctrl+F4나 창 닫기는 최고점수를 반영하고 종료합니다.

현재 입력 순서에서는 게임오버 중에도 Esc로 정지를 켤 수 있습니다. 이때 Enter가 무시되므로 Esc로 정지를 풀고 Enter를 눌러야 재시작합니다. 현재 동작을 이해하는 것과 앞으로 입력 규칙을 개선할지는 별개로 다룹니다.

`reset()`은 플레이어 위치·속도·점프, 장애물과 대기열, 모션, 배경 시계·위치, 점수와 판 상태를 새로 준비합니다. 최고점수와 이미 로딩한 자산은 유지합니다. 처음 시작과 재시작이 같은 초기화 함수를 사용하면 상태를 하나만 돌려놓는 실수를 줄일 수 있습니다. `stop()`은 기록을 반영하고 `running`을 False로 만들어 반복을 끝냅니다.

## 17. 계산 결과를 화면으로 옮기는 순서

그림은 나중에 그린 것이 앞에 올라옵니다. 현재 출력은 배경 두 장→장애물→플레이어 포즈→점수→게임오버·정지 안내 순서이며, `pygame.display.flip()`으로 완성한 화면을 보여 줍니다. 정지 안내를 마지막에 놓으면 화면 위에 어두운 덮개와 문구를 표시할 수 있습니다.

백이 `game_over=True`라고 결정하는 일과 프론트가 GAME OVER를 그리는 일은 서로 연결된 두 작업입니다. 점수도 백의 숫자가 바뀌기만 해서는 화면에 보이지 않습니다. 프론트가 `state.score`를 읽어 글자를 만들어야 합니다.

## 18. 테스트는 상황을 대신 만들어 보는 코드

테스트는 게임을 시작할 때 자동으로 실행되는 기능이 아니라 개발자가 고장 여부를 확인하는 코드입니다. 현재 테스트는 화면 없는 SDL 드라이버를 사용하며 실제 게임 객체와 이미지로 계산합니다. `pygame.event.post()`로 Space·Enter·창 닫기 같은 이벤트를 넣고 결과 상태를 확인할 수도 있습니다.

예를 들어 Space 뒤 y가 작아지는지, 정지 중 값이 유지되는지, 충돌 후 재시작이 되는지, 계절 경계와 해금 시점이 맞는지, 화면 프레임과 마스크가 맞는지 검사합니다. `unittest.mock.patch`로 무작위 선택을 고정하면 원하는 장애물이나 패턴을 재현할 수 있습니다.

최고점수 검사는 임시 폴더의 별도 파일을 사용합니다. 실제 `txt/high_score.txt`를 시험 점수로 바꾸지 않기 위해서입니다. 백만 검사할 때는 화면과 PNG를 준비하지 않고 크기와 마스크를 전달할 수 있어 역할 분리의 효과도 확인할 수 있습니다.

테스트를 읽을 때는 어떤 상황을 만들었는지, 무엇을 실행했는지, 어떤 결과를 기대하는지 순서로 보세요. 이전 문서의 검사 개수는 당시 기록이므로 현재 결과와 혼동하지 않습니다. 자동 검사가 통과해도 실제 창에서 모션, 발 위치와 조작감을 확인해야 합니다.

| `RUN_FRAME_TICKS`를 6에서 12로 바꾸면? | 한 포즈가 0.2초, 네 포즈 한 바퀴가 0.8초가 됩니다. |
| FPS를 120에서 60으로 바꾸면 속도도 절반일까요? | 정상적인 시간 계산에서는 초당 이동 거리를 유지하고 그리는 횟수가 줄어듭니다. |
| `OBSTACLE_SPEED`를 6에서 8로 바꾸면? | 기본 초당 이동량은 360에서 480픽셀이 됩니다. 같은 값을 사용하는 배경도 빨라지며 누적 가속은 따로 적용됩니다. |
| `PASS_BONUS`를 10에서 20으로 바꾸면? | 장애물 하나의 통과 보너스가 20점이며 생존 점수는 별도입니다. |
| `CHARACTER_HEIGHT`를 180으로 바꾸면 기본 상찌는? | `CHARACTER_HEIGHT // 3`이므로 높이 60이 됩니다. 바닥·화면·충돌·회피 조건도 다시 확인해야 합니다. |
| 점프 속도를 -15에서 -18로 바꾸면? | 다른 조건이 같으면 더 강하게 위로 올라가고 착지 시간도 바뀝니다. |
| Esc를 누르면 저장하고 종료할까요? | 정지·재개입니다. 종료 입력은 Ctrl+F4나 창 닫기입니다. |
| `passed`는 왜 필요할까요? | 같은 장애물의 통과 보너스를 반복 지급하지 않기 위해서입니다. |

## 21. 예전 설명에서 달라진 점

2026-11-07의 입문 노트에는 한 파일에서 게임 전체를 읽던 방식, 사각형을 줄이는 충돌, 통과 점수 중심의 설명과 그때의 미구현 목록이 있었습니다. 이후 역할별 파일 분리, 실제 출력 마스크 충돌, 생존 점수와 누적 가속, 사계절 낮밤 전환, 유형별 장애물과 모션으로 학습 범위가 넓어졌습니다.

현재 실행은 `main.py`, 검사는 `tests/`를 사용합니다. 이전 `prototype_game.py` 실행 명령, `test/` 경로, 사라진 `HITBOX_SHRINK` 설정과 “밤 전환이 없다”는 문장을 현재 사양으로 사용하지 않습니다. 과거 자료에서 배우는 원리와 현재 코드의 동작을 나누어 읽는 것도 개발 문서를 관리하는 연습입니다.

새로 공부할 때는 `config → main.main/run → handle_events → backend.reset/jump/update/update_step → frontend.draw` 순으로 읽고, 이미지와 저장이 궁금할 때 assets와 storage를 봅니다. 그다음 tests에서 같은 동작을 코드로 재현하는 방법을 살펴보세요. 현재 동작의 자세한 확인은 [ARCHITECTURE](ARCHITECTURE.md), 다음에 만들 기능과 실험은 [GAME_IDEA](GAME_IDEA.md)로 이어집니다.
