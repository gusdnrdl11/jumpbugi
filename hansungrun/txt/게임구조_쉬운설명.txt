한성런 코드 구조 설명서
현재 코드 기준 / 처음 읽는 사람을 위한 설명
======================================================================

1. 가장 먼저 이해할 것
----------------------------------------------------------------------

이 게임의 큰 역할은 여전히 '진행을 연결하는 메인, 화면을 보여 주는 프론트,
게임 규칙을 계산하는 백'입니다.

다만 프론트와 백 안에 모든 일을 집어넣는 대신, 반복해서 쓰는 일과 성격이
다른 일을 작은 보조 파일로 꺼내 두었습니다.

  main.py       : 게임을 시작하고, 입력 → 계산 → 화면 출력을 반복한다.
  frontend.py   : 현재 게임 상태를 화면에 보여 준다.
  backend.py    : 위치, 점프, 충돌, 점수 같은 게임 상태를 계산한다.

  config.py     : 숫자와 파일 위치를 모아 둔 설정표다.
  assets.py     : 그림을 읽고, 크기를 맞추고, 달리기 그림을 나눈다.
  storage.py    : 최고점수 파일을 읽고 저장한다.

  tests/test_game.py : 위 코드가 제대로 움직이는지 자동으로 확인한다.
  __init__.py   : 이 폴더를 파이썬 패키지로 다룰 때 사용하는 파일이다.

즉, 게임이 여러 개가 된 것이 아닙니다.
한 게임을 만드는 코드를 담당 업무에 따라 여러 파일에 담은 것입니다.
실행할 때도 파일을 하나씩 따로 실행하지 않습니다. main.py를 실행하면 됩니다.

여기서 '백'은 인터넷 서버를 뜻하지 않습니다.
현재 게임은 같은 컴퓨터에서 하나의 파이썬 프로그램으로 실행됩니다.
백은 그 안에서 게임 규칙을 담당하는 부분을 부르는 이름입니다.


2. 식당에 비유하면 쉽다
----------------------------------------------------------------------

main.py는 진행 담당자입니다.
주문이 들어왔는지 확인하고, 요리를 요청하고, 완성된 것을 내보내게 합니다.

backend.py는 요리사입니다.
정해진 규칙에 따라 실제 결과를 만듭니다.
게임에서는 '캐릭터가 어디에 있는가, 부딪혔는가, 점수가 얼마인가'를 결정합니다.

frontend.py는 손님에게 보이는 접시와 진열을 담당합니다.
백이 계산한 결과를 그림과 글자로 보여 줍니다.

config.py는 공통 기준표입니다.
'몇 그램을 쓸지'를 적듯, 화면 크기와 점프 속도 같은 값을 적습니다.

assets.py는 재료 준비 담당입니다.
그림 파일을 사용할 수 있도록 읽고 크기를 맞춥니다.

storage.py는 기록 담당입니다.
영업이 끝나도 남겨야 하는 기록처럼, 게임을 꺼도 남아야 하는 최고점수를 씁니다.

tests/test_game.py는 점검표입니다.
정해진 상황을 만들어 보고 예상한 결과가 나오는지 검사합니다.

요리사가 기록장 정리까지 전부 할 수도 있지만, 업무를 나누면 무엇을
고칠 때 누구의 작업을 봐야 하는지 찾기 쉬워집니다. 코드도 같은 이유입니다.


3. 파일들이 연결되는 실제 모양
----------------------------------------------------------------------

  사용자가 main.py 실행
           |
           v
       main.py
       /     \
      v       v
 frontend.py  backend.py
      |           |
      v           v
  assets.py   storage.py

  config.py의 설정은 main, frontend, backend, assets가 가져다 씁니다.
  tests/test_game.py는 게임을 만들어 입력과 상태 변화를 검사합니다.

이 그림의 화살표는 '다른 파일의 기능을 가져다 쓴다'는 의미입니다.
각 파일이 별도 프로그램이나 별도 서버로 실행된다는 의미는 아닙니다.

중요한 연결 하나가 더 있습니다.
main은 frontend가 읽은 그림의 크기를 backend에 전달합니다.
backend는 그림 자체를 받지 않고 '가로·세로 크기' 같은 필요한 정보만 받습니다.
그리고 frontend는 그릴 때 backend의 현재 상태를 전달받습니다.

  프론트가 준비한 이미지 크기 → 메인 → 백의 충돌 계산
  백의 좌표·점수·게임오버 여부 → 메인 → 프론트의 화면 출력


4. main.py: 모든 일을 직접 하기보다 실행 순서를 연결한다
----------------------------------------------------------------------

main.py의 주요 이름은 HansungRun입니다.
이 클래스는 게임 한 개를 관리하는 묶음이라고 생각하면 됩니다.

클래스 안의 self.view에는 GameView 객체가 들어갑니다.
쉽게 말해 '이번 게임의 화면 담당자'를 저장해 둡니다.

self.state에는 GameState 객체가 들어갑니다.
쉽게 말해 '이번 게임의 현재 상황과 계산 담당자'를 저장해 둡니다.

게임을 처음 만들 때의 순서는 다음과 같습니다.

  ① GameView()를 만든다.
     창을 만들고, 이미지와 글꼴을 준비한다.

  ② 준비된 이미지의 크기, 달리기 그림 수, 배경 너비를 알아낸다.

  ③ 그 정보를 주면서 GameState(...)를 만든다.
     백은 그 크기로 위치와 충돌을 계산할 준비를 한다.
     이때 기존 최고점수도 읽는다.

  ④ 시간을 재는 clock을 만든다.

그다음 run()이 반복됩니다.

  경과 시간 확인
        ↓
  handle_events(): 키와 창 닫기 입력 확인
        ↓
  update(dt): 백에게 다음 상태 계산 요청
        ↓
  draw(): 프론트에게 현재 상태를 그려 달라고 요청
        ↓
  다시 반복

dt는 '지난번 반복 이후 흐른 시간(초)'입니다.
예를 들어 0.01이면 약 0.01초가 지났다는 뜻입니다.
컴퓨터마다 반복 횟수가 조금 달라도, 흐른 시간을 고려해 이동하게 합니다.

FPS=120은 반복 속도의 상한 목표입니다.
모든 컴퓨터에서 무조건 초당 120번 실행된다는 보장은 아닙니다.
PHYSICS_HZ=60은 기존 이동·중력 수치를 시간에 맞게 계산하는 기준입니다.
화면 반복 속도와 물리 계산의 기준을 구별해 둔 것입니다.

입력 처리도 메인이 맡습니다.

  Space    → 백의 jump() 호출
  Esc      → 백의 paused 값 변경
  Enter    → 게임오버 상태에서 reset() 호출
  Ctrl+F4  → 백의 stop() 호출
  창 닫기  → 백의 stop() 호출

현재 메인은 일시정지 값을 직접 바꾸기도 합니다.
모든 상태 변경을 백의 함수로만 하도록 엄격히 제한한 구조는 아닙니다.

파일 마지막의 다음 코드는 시작 버튼에 해당합니다.

  if __name__ == "__main__":
      main()

'이 파일을 직접 실행했으면 main()을 호출하라'는 뜻입니다.
다른 파일이 import해서 가져올 때는 이 부분으로 게임을 자동 시작하지 않습니다.
main()은 pygame을 초기화하고 게임을 실행하며, 끝날 때 pygame을 종료합니다.


5. backend.py: 게임에서 일어난 사실과 규칙을 관리한다
----------------------------------------------------------------------

주요 이름은 GameState입니다. state는 '현재 상태'라는 뜻입니다.

현재 상태의 예:

  player_y       : 캐릭터의 세로 위치
  velocity_y     : 위아래로 움직이는 속도
  is_jumping     : 지금 점프 중인지
  obstacle_x     : 장애물의 가로 위치
  obstacle_name  : 현재 장애물 종류
  score          : 이번 판 점수
  high_score     : 최고점수
  game_over      : 게임이 끝났는지
  paused         : 일시정지 중인지
  running        : 프로그램의 게임 반복을 계속할지
  night_alpha    : 밤 배경을 얼마나 진하게 보여 줄지

변수는 현재 상황을 적어 둔 칸이고, 함수는 그 상황을 바꾸는 행동입니다.

  reset()             : 새 판을 시작할 상태로 돌린다.
  jump()              : 점프 가능한지 확인하고 위쪽 속도를 준다.
  spawn_obstacle()    : 장애물 종류와 시작 위치를 정한다.
  update()            : 시간이 흐른 만큼 게임을 진행한다.
  update_step()       : 이동·중력·충돌·점수를 세부적으로 계산한다.
  update_background(): 낮밤 전환에 필요한 값을 계산한다.
  record_high_score(): 신기록이면 저장 담당에게 저장을 요청한다.
  stop()              : 기록을 반영하고 반복 종료 상태로 만든다.

점프를 예로 들면, 백은 이미지를 위로 그리는 작업을 하지 않습니다.
player_y라는 숫자를 바꿉니다. 프론트가 그 숫자의 위치에 그림을 그립니다.

pygame 화면의 세로 좌표는 아래로 갈수록 커집니다.
그래서 JUMP_SPEED=-15처럼 음수 속도로 시작하면 위로 움직입니다.
중력이 속도를 점점 아래 방향으로 바꾸고, 바닥에 닿으면 점프가 끝납니다.

충돌할 때는 캐릭터와 장애물의 사각형을 만들어 겹치는지 확인합니다.
그림 전체보다 검사 사각형을 줄여, 눈으로 보기에 떨어져 있는데도
충돌하는 느낌을 줄이도록 보정합니다.

백도 pygame을 import합니다. 사각형 계산에 pygame.Rect를 쓰기 때문입니다.
따라서 '백에는 pygame이 전혀 없다'는 구조는 아닙니다.
화면을 만드는 일과 그리는 일을 백에서 하지 않는 것이 핵심입니다.

또한 현재 백에는 게임 규칙 외에 달리기 애니메이션 시간과 낮밤 전환 시간도
있습니다. 시간에 따라 바뀌는 값을 백에서 계산하고, 실제 그림 표현은
프론트에서 하도록 나누어 놓았습니다.


6. frontend.py: 계산된 사실을 눈에 보이게 만든다
----------------------------------------------------------------------

주요 이름은 GameView입니다. view는 '보여 주는 부분'이라는 뜻입니다.

처음에는 게임 창, 배경 그림, 캐릭터 그림, 장애물 그림, 글꼴,
게임오버 문구, 일시정지 안내 등을 준비합니다.

draw(state)는 백의 상태를 보고 아래 순서로 그립니다.

  배경 → 장애물 → 캐릭터 → 점수 → 게임오버·일시정지 안내

뒤에 그린 것이 앞에 그린 것 위에 보이므로 순서가 중요합니다.

백에서 score가 10이 되었다고 해서 화면 글자가 저절로 바뀌지는 않습니다.
프론트가 state.score를 읽어 'SCORE 10'이라는 글자를 그려야 보입니다.

백에서 game_over가 True가 되면, 프론트는 그 값을 보고
GAME OVER 문구를 보여 줍니다.

정리하면 같은 게임오버에도 두 가지 일이 있습니다.

  백    : 부딪혔으므로 게임오버라고 결정한다.
  프론트: 그 결정을 보고 안내 문구를 그린다.

sync_background(alpha)는 낮 그림과 밤 그림을 섞습니다.
alpha=0이면 낮, 255이면 밤, 그 사이면 전환 중인 모습입니다.
백은 얼마나 섞을지 계산하고, 프론트는 실제 이미지 합성을 합니다.


7. assets.py: '그림 준비'를 프론트에서 따로 꺼낸 이유
----------------------------------------------------------------------

이 파일도 넓게 보면 프론트를 돕는 코드입니다.
프론트와 동급의 새로운 게임 계층이 꼭 하나 더 생긴 것은 아닙니다.

load_image()는 그림을 읽고 필요하면 크기를 조절합니다.
height를 지정하면 가로세로 비율을 유지하면서 높이에 맞춥니다.
size를 지정하면 그 크기에 맞춥니다.

load_run_frames()는 2×2로 묶인 달리기 그림을 네 장으로 나눕니다.
각 칸의 캐릭터 주변 여백을 정리하고, 공통 배율과 발 위치에 맞춥니다.
프레임마다 캐릭터가 갑자기 커지거나 발이 들쭉날쭉해지는 것을 줄입니다.

왜 따로 뒀을까요?

프론트에서 배경을 그리는 코드를 보려는데 이미지 자르기 계산이 길게
섞여 있으면 읽기 어렵습니다. 따로 꺼내면 프론트에서는
'달리기 그림들을 준비해 줘'라는 한 줄로 의도를 알 수 있습니다.

또한 여러 그림에서 같은 로딩·크기 조절 코드를 복사할 필요가 줄어듭니다.
그림 처리 방식을 고칠 때 assets.py의 공통 함수를 고치면 됩니다.

현재 이미지는 프론트 초기화 때 준비합니다.
매번 화면을 그릴 때마다 디스크에서 이미지를 다시 읽는 구조가 아닙니다.


8. storage.py: '점수 판단'과 '파일 저장 방법'을 나눈 이유
----------------------------------------------------------------------

백이 결정할 일:
  이번 점수가 최고점수보다 높은가? 언제 저장할 것인가?

storage가 처리할 일:
  어느 파일에서 숫자를 읽고, 어떤 순서로 파일에 쓸 것인가?

load_high_score(path)는 파일의 글자를 읽어 정수로 바꿉니다.
파일이 없으면 첫 실행이라고 보고 0을 돌려줍니다.
현재는 숫자가 아닌 내용이나 음수 기록을 자동으로 복구하지는 않습니다.
그런 경우에는 오류가 발생합니다.

save_high_score(path, score)는 저장 폴더를 준비하고,
임시 파일에 먼저 쓴 다음 실제 기록 파일을 교체합니다.
실제 기록 파일을 곧바로 비우고 쓰는 일을 피하는 방식입니다.
모든 종류의 저장 실패나 전원 차단을 완전히 막는다는 뜻은 아닙니다.

백에서는 '신기록을 저장해 줘'라고 요청하면 됩니다.
파일을 여는 세부 코드를 점프나 충돌 계산 사이에서 읽지 않아도 됩니다.

나중에 저장 형식을 바꾸면 storage와 필요한 연결 부분을 검토하면 됩니다.
현재 함수의 사용 방법을 유지할 수 있다면 백의 변경을 줄일 수 있습니다.


9. config.py: 여러 파일이 함께 보는 설정표
----------------------------------------------------------------------

게임 속도나 크기 같은 값을 코드 여기저기에 적으면 수정할 때 놓치기 쉽습니다.
예를 들어 한쪽은 캐릭터 높이를 120, 다른 쪽은 100이라고 알면
그림과 충돌 계산이 서로 맞지 않을 수 있습니다.

그래서 여러 부분이 같은 기준으로 써야 하는 값을 모아 둡니다.

현재 값의 예:

  SCREEN_SIZE=(480, 360)       : 게임 창 크기
  FPS=120                      : 화면 반복 속도의 상한 목표
  CHARACTER_HEIGHT=120         : 기본 캐릭터 높이
  OBSTACLE_SPEED=6             : 60Hz 기준 장애물 이동량
  BACKGROUND_SPEED             : 배경 이동 속도, 현재 장애물 속도와 같은 값
  JUMP_SPEED=-15               : 점프 시작 속도
  GRAVITY=0.6                  : 아래로 당기는 정도
  PASS_BONUS=10                : 장애물 통과 보너스
  DAY_NIGHT_INTERVAL=30.0      : 낮밤 전환 주기
  BACKGROUND_FADE_SECONDS=3.0 : 전환을 섞어서 보여 주는 시간

상찌는 OBSTACLE_HEIGHTS에서 기본 높이의 1/3, 즉 40으로 설정되어 있습니다.

설정표에는 파일 위치도 있습니다.
여기서 PROJECT_DIR은 config.py가 있는 hansungrun 폴더입니다.
현재 배치는 다음과 같습니다.

  hansungrun/
    main.py, frontend.py, backend.py
    config.py, assets.py, storage.py, __init__.py
    image/                  ← 그림·원본·계절 배경·미리보기
    txt/
      high_score.txt        ← 실제 최고점수
      기타 기존 텍스트 자료
    tests/
      __init__.py
      test_game.py          ← 기본 동작 검사
      test_game09.py        ← 상세 회귀 검사
    docs/
      README.md             ← 문서 목차와 실행 안내
      TODO.md               ← 다음 작업
      CHANGELOG.md          ← 완료 작업
      ARCHITECTURE.md       ← 현재 구조
      STUDY_NOTES.md        ← 학습 노트
      게임구조_쉬운설명.txt  ← 지금 읽는 문서
      archive/              ← 이전 문서와 배경 작업 자료

그림은 hansungrun/image, 기록은 hansungrun/txt에서 찾습니다.
상위 폴더의 image와 txt는 내부로 이동했습니다.
config.py의 실제 위치를 기준으로 찾으므로 터미널의 현재 위치가 바뀌어도
같은 그림과 기록을 사용합니다. 프로젝트를 옮길 때 내부 폴더도 함께 옮깁니다.
문서 목차는 같은 docs 폴더의 README.md에서 확인할 수 있습니다.

설정값은 실행 중 편집한다고 화면에 자동 반영되는 구조는 아닙니다.
값을 고쳤다면 게임을 다시 실행해서 확인하면 됩니다.


10. tests/test_game.py와 __init__.py는 왜 있는가?
----------------------------------------------------------------------

tests/test_game.py는 플레이어에게 기능을 제공하는 파일이 아닙니다.
개발자가 수정 후 고장 여부를 확인하기 위한 파일입니다.
main.py가 게임을 시작할 때 이 테스트를 자동으로 실행하지도 않습니다.

현재 테스트는 실제 게임 객체와 이미지를 사용하되, 눈에 보이는 창 대신
화면 없는 방식으로 실행합니다. 키 입력과 종료 이벤트를 코드로 넣고,
상태가 예상대로 바뀌는지 확인합니다.

검사하는 예:
  Space를 넣으면 위로 올라가는가?
  일시정지 중에는 위치가 유지되는가?
  다시 진행하면 착지하는가?
  충돌하면 게임오버가 되는가?
  Enter를 넣으면 새 판으로 돌아가는가?
  장애물을 지나면 점수가 오르는가?
  밤 전환값이 바뀌는가?
  종료하면 테스트용 최고점수 파일에 기록되는가?

테스트는 임시 폴더의 별도 기록 파일을 사용합니다.
사용자의 실제 최고점수를 테스트 점수로 바꾸지 않기 위해서입니다.
단, 자동 테스트가 통과해도 실제 창의 외관이나 조작감을 모두 보장하지는 않습니다.

__init__.py는 이 폴더를 파이썬 패키지로 다루는 데 쓰입니다.
현재는 설명만 있고, 게임 규칙은 들어 있지 않습니다.
게임 실행 파일로 사용할 필요도 없습니다.


11. Space 한 번을 눌렀을 때의 전체 여행
----------------------------------------------------------------------

  ① main.py가 Space 입력을 받는다.

  ② main.py가 self.state.jump()를 호출한다.

  ③ backend.py의 jump()가 정지·게임오버·점프 중인지 확인한다.
     가능하면 위로 움직이는 속도를 설정하고 점프 중으로 바꾼다.

  ④ main.py가 update(dt)를 호출한다.

  ⑤ backend.py가 시간과 중력을 적용해 player_y를 바꾼다.

  ⑥ main.py가 draw()를 호출한다.

  ⑦ frontend.py가 바뀐 player_y를 읽고 그 위치에 캐릭터를 그린다.

  ⑧ 반복되면서 눈에는 캐릭터가 점프하는 것처럼 보인다.

이 과정에서 storage는 할 일이 없습니다. 점프할 때 파일을 저장할 필요가
없기 때문입니다. 모든 기능이 모든 파일을 거치는 것은 아닙니다.


12. 장애물 충돌부터 기록 저장까지
----------------------------------------------------------------------

  ① backend.py가 캐릭터와 장애물의 충돌을 확인한다.

  ② 충돌했다면 game_over=True로 만든다.

  ③ 이번 점수가 최고점수보다 높은지 백이 확인한다.

  ④ 높으면 storage.py의 save_high_score()를 호출한다.
     저장할 위치는 config.py에서 정한 경로를 기본으로 사용한다.

  ⑤ frontend.py가 game_over 값을 보고 GAME OVER를 그린다.

  ⑥ Enter 입력을 main.py가 받으면 백의 상태를 초기화한다.
     프론트의 배경도 초기화한 상태에 맞춘다.

game_over와 running은 다릅니다.
game_over=True이면 이번 판 진행은 멈추지만 창과 입력 처리는 계속됩니다.
그래야 Enter로 재시작할 수 있습니다.
running=False이면 메인의 반복 자체가 끝나 게임 실행이 종료됩니다.

현재 최고점수는 매 통과 순간마다 저장하지 않습니다.
게임오버가 되거나 정상 종료를 요청할 때 신기록을 반영합니다.


13. 프론트와 백 두 파일만으로 만들면 안 되는가?
----------------------------------------------------------------------

두 파일만으로도 만들 수 있습니다. 틀린 구조가 아닙니다.

예를 들어 이렇게 합칠 수 있습니다.

  프론트 파일 = 화면 출력 + 이미지 준비
  백 파일     = 게임 규칙 + 최고점수 저장
  설정값      = 두 파일 중 한 곳 또는 각각에 작성

하지만 이미지 자르기 코드가 길어지고 저장 처리도 늘어나면,
프론트와 백 각각에서 서로 다른 종류의 일을 한꺼번에 읽어야 합니다.

현재 구조는 아래 질문에 빨리 답하기 위해 보조 파일을 뒀습니다.

  '점프가 이상한가?'        → backend.py
  '글자 위치가 이상한가?'   → frontend.py
  '모션 그림 정렬 문제인가?'→ assets.py
  '기록이 저장되지 않는가?' → storage.py
  '속도만 바꾸고 싶은가?'   → config.py
  '입력과 실행 연결 문제인가?' → main.py

파일을 나누는 주된 이유는 실행 속도를 높이기 위해서가 아닙니다.
찾기 쉽게 하고, 수정 범위를 줄이고, 따로 확인하기 위해서입니다.
이미지를 한 번만 준비하는 등의 실행 방식은 성능에 영향을 주지만,
단순히 파일 개수가 늘었다고 게임이 빨라지는 것은 아닙니다.

단점도 있습니다.
처음에는 여러 파일을 오가야 해서 흐름이 더 어려워 보일 수 있습니다.
import 연결을 관리해야 하고, 잘못 나누면 파일끼리 얽힐 수도 있습니다.
작은 게임에서 함수 하나마다 파일을 만드는 식으로 계속 쪼갤 필요는 없습니다.

현재 assets와 storage는 프론트·백을 돕는 작은 도구라고 받아들이면 됩니다.
'게임의 중심은 메인·프론트·백, 반복 작업은 보조 파일' 정도로 이해하면 충분합니다.


14. 실제로 무언가 바꾸고 싶을 때 어디를 열까?
----------------------------------------------------------------------

  점프를 더 높게 하고 싶다.
    → config.py의 JUMP_SPEED와 GRAVITY를 먼저 본다.
      점프 계산 방식 자체를 바꿀 때는 backend.py를 본다.

  점수 글자색이나 위치를 바꾸고 싶다.
    → frontend.py의 draw()를 본다.
      공통 여백 수치는 config.py의 HUD_MARGIN, HUD_GAP에 있다.

  점프 키를 다른 키로 바꾸고 싶다.
    → main.py의 handle_events()를 본다.

  통과 보너스를 20점으로 바꾸고 싶다.
    → config.py의 PASS_BONUS를 바꾼다.
      점수를 주는 조건 자체를 바꾸려면 backend.py를 본다.

  장애물 그림 한 종류를 더 넣고 싶다.
    → image 폴더에 그림을 추가하고 config.py의 OBSTACLE_FILES와
      높이 설정을 확인한다. 프론트와 백은 이 목록을 이용한다.
      특수 행동을 하는 장애물이면 백의 규칙도 추가로 바꿔야 한다.

  달리기 그림이 2×2가 아닌 다른 배열로 바뀌었다.
    → assets.py의 load_run_frames() 분할 방식을 바꾼다.

  최고점수 파일 위치를 바꾸고 싶다.
    → config.py의 HIGH_SCORE_PATH를 본다.

  최고점수를 저장하는 파일 형식을 바꾸고 싶다.
    → storage.py의 읽기·저장 함수를 본다.

  캐릭터가 실제로 닿기도 전에 게임오버가 된다.
    → backend.py의 충돌 계산과 config.py의 HITBOX_SHRINK 값들을 본다.
      그림의 투명 여백이나 크기 문제인지도 함께 확인한다.

항상 한 파일만 수정하면 된다는 뜻은 아닙니다.
새 기능이 여러 역할에 걸쳐 있으면 관련 파일을 함께 바꾸는 것이 자연스럽습니다.
예를 들어 무적 아이템은 백에 무적 규칙, 프론트에 표시,
assets에 이미지 준비, config에 지속 시간 등이 필요할 수 있습니다.


15. import 부분이 두 갈래인 이유
----------------------------------------------------------------------

여러 파일 윗부분에 if __package__: 와 else:가 있습니다.
게임 규칙을 두 번 실행하려는 코드가 아닙니다.
파이썬이 다른 파일을 찾는 두 가지 실행 방식을 지원하기 위한 코드입니다.

  방법 A: hansungrun 폴더에서
    python main.py

  방법 B: 한 단계 위 폴더에서
    python -m hansungrun.main

방법 A에서는 'from backend import ...'처럼 같은 폴더의 파일을 찾습니다.
방법 B에서는 'from .backend import ...'처럼 같은 패키지 안의 파일을 찾습니다.
앞의 점 하나는 '현재 패키지 안에서 찾는다'는 표시입니다.

현재 코드는 두 경우를 구분해서 알맞은 import를 사용합니다.
처음 공부할 때는 이 부분을 실행 방식에 맞는 파일 연결 장치로 이해하고,
그 아래 클래스와 함수부터 읽어도 됩니다.


16. 처음 공부할 때 추천하는 읽는 순서
----------------------------------------------------------------------

  ① config.py
     화면 크기와 점프 속도 등 게임의 기본 숫자를 본다.

  ② main.py의 main()과 run()
     어디서 시작해서 어떤 순서로 반복하는지 본다.

  ③ main.py의 handle_events()
     어떤 입력이 어떤 행동으로 연결되는지 본다.

  ④ backend.py의 reset(), jump(), update(), update_step()
     상태가 어떻게 시작하고 변하는지 본다.

  ⑤ frontend.py의 draw()
     그 상태를 어떻게 화면으로 바꾸는지 본다.

  ⑥ assets.py와 storage.py
     필요한 순간에 이미지 준비와 기록 저장의 세부 방법을 읽는다.

  ⑦ tests/test_game.py
     직접 게임을 조작하는 대신 코드가 상황을 만드는 방식을 본다.

실행 명령: hansungrun 폴더에서 python main.py
테스트 명령: 같은 폴더에서 python -B -m unittest discover -s tests -v

처음부터 모든 줄을 외울 필요는 없습니다.
먼저 '입력은 메인, 판단은 백, 표현은 프론트'를 잡고,
설정·이미지 준비·파일 저장은 옆에서 돕는 도구라고 생각하면 됩니다.
